# Translating the documentation site

English is the source language. It lives at the root of `src/content/docs/` and is served
without a URL prefix, exactly as before this site had a second language:

```
src/content/docs/start/quickstart.md      →  /CrystalBackup/docs/start/quickstart/
```

French lives in `src/content/docs/fr/`, mirroring the English tree file for file, and is
served under `/fr/`:

```
src/content/docs/fr/start/quickstart.md   →  /CrystalBackup/fr/docs/start/quickstart/
```

**No English URL may move.** The README, the published crucible reports and external links
all point into `/CrystalBackup/docs/…`. Adding a language was verified to be purely
additive — 33 French pages appeared, zero English pages changed path. Keep it that way.

A page that has not been translated yet is not a 404 under `/fr/`. Starlight serves the
English content with a "this page is not yet available in your language" notice. That is
the honest state, and it is what the translation effort removes page by page.

---

## The one rule: `sourceHash`

Every translated page records the git blob hash of the exact English bytes it was
translated from:

```yaml
---
title: Démarrage rapide
description: Un premier backup du plan cluster et un premier restore…
sourceFile: src/content/docs/start/quickstart.md
sourceHash: d45723165d3c56b6c52bcde8c08f3b30aa230668
---
```

This exists because a translated page that has silently fallen behind is **worse than no
translation**. A reader trusts a stale page exactly as much as a fresh one, and nothing in
a normal review catches the drift: the French file is untouched, so it never appears in the
diff that broke it. On a site whose subject is losing data, a French page still promising a
field that was renamed two releases ago is a real incident waiting for a reader.

A blob hash changes if and only if the file's bytes change. So editing an English page
breaks every translation of it *in the same pull request that made the edit* — the only
moment at which somebody still knows what changed and why.

## Adding a translated page

1. Copy the English file into the mirror position. The path under `fr/` must match the
   English path exactly; the checker rejects anything else.

   ```bash
   cd website
   cp src/content/docs/start/install.md src/content/docs/fr/start/install.md
   ```

2. Get the source hash:

   ```bash
   git hash-object src/content/docs/start/install.md
   ```

3. Add `sourceFile` and `sourceHash` to the French frontmatter. `sourceFile` is the path
   relative to `website/`, and `sourceHash` is the value from step 2.

4. Translate. Then check:

   ```bash
   make check-translations        # from the repository root
   ```

### What to translate, and what not to

Prose is French. Everything a reader would type or grep for stays exactly as it is in
English:

- **never translated**: code blocks, shell commands, YAML keys and values, CRD kinds and
  field names (`ClusterBackupLocation`, `spec.locationRef`, `confirmation`), metric and
  alert names, label keys, phase and condition strings (`Ready`, `AwaitingConfirmation`,
  `CSISnapshotUnsupported`), and the expected command output;
- **kept in English inside French sentences**: the domain vocabulary this project's readers
  already use — backup, restore, snapshot, repository, namespace, cluster, tenant, pod,
  volume, mover, schedule, location, bucket, credentials. "Une backup location du plan
  cluster" reads correctly to a French SRE; "un emplacement de sauvegarde" does not, and it
  is also ungreppable against the API;
- **translated**: everything else, including admonition titles
  (`:::caution[Pas encore exécuté de bout en bout]`) and link text.

Internal links get the `fr/` segment: `/CrystalBackup/fr/docs/guides/restore/`. Linking to
the English URL from a French page silently ejects the reader from the locale.

Sidebar labels are not in the page — they live in `astro.config.mjs`, as a `translations:
{ fr: '…' }` map on each entry. Autogenerated groups take their labels from page titles
instead, so those become French as the pages do.

## When the English page changes

The check fails, by design, and names both the page and the hashes:

```
ERROR: 1 translation problem(s):
  - src/content/docs/fr/start/quickstart.md: STALE. src/content/docs/start/quickstart.md
    has changed since this page was translated.
           recorded: d45723165d3c56b6c52bcde8c08f3b30aa230668
           current:  53d949b38da549ecc91760fc5f0f15a90634dbb0

  A stale page is served with the same confidence as a fresh one, which is why
  this fails the build. Re-read the English diff, update the French text, then:

      make translations-refresh
```

Do it in that order:

```bash
git diff <base> -- website/src/content/docs/start/quickstart.md   # what actually changed
$EDITOR website/src/content/docs/fr/start/quickstart.md           # carry the change over
make translations-refresh                                          # stamp the new hash
```

`make translations-refresh` **only stamps the hash**. It translates nothing. Running it
without carrying the change over certifies a page that is now wrong, and does so in green —
which is the precise failure this whole mechanism exists to prevent. It prints every page it
touched so that a reviewer can see what was certified.

If the English page was **deleted or renamed**, the check says so instead
(`its English source … no longer exists`) and the fix is to move or delete the French file
to match.

---

## What the check will and will not fail on

| Situation | Result |
| --- | --- |
| French page's `sourceHash` ≠ current hash of the English file | **error** |
| French page's English source no longer exists | **error** |
| French page with no `sourceFile` / no `sourceHash` / a malformed hash | **error** |
| `sourceFile` naming a file other than the page's own mirror position | **error** |
| A locale declared in `src/i18n/locales.mjs` with no translated page at all | **error** |
| Zero translated pages, or zero English pages, or no `git` on `PATH` | **error** |
| An English page with no French counterpart | *warning* |

The last row is the only soft one, and it is deliberate. The site has ~36 pages and one of
them is translated today, on purpose: this lot shipped the mechanism, the bulk translation
is separate work. Making the gap an error would mean the check is red from the minute it
lands, and a permanently-red check is one people learn to skip — the same silence in a
louder costume. **When French coverage is complete, flip it**: add
`--require-full-coverage` to the `make check-translations` invocation (or set
`I18N_REQUIRE_FULL_COVERAGE=1`), and the gap becomes an error like everything else.

Everything above is enforced by `website/tools/check-translations.mjs`, which is stdlib-only
and needs no `npm install`. `make check-translations` runs the checker's own self-test first
— fixture trees exercising drift, a vanished source, a missing key, a redirected
`sourceFile` and an empty locale — and only then the real check, so the job cannot report
green without having just watched the guard go red.

## Adding another language

1. Add it to `LOCALES` in `src/i18n/locales.mjs`. That one table feeds Starlight's locale
   config, the entry-id shape in `src/content.config.ts` and the staleness checker; nothing
   restates it, because a guard that learns the language list somewhere other than the site
   does is a guard that can pass while covering nothing that shipped.
2. Add `translations: { <locale>: '…' }` to the sidebar entries in `astro.config.mjs`.
3. Create `src/content/docs/<locale>/` and translate at least one page — the check fails on
   a declared locale whose directory is empty, because every URL under it would be an
   unwatched English fallback.

## The landing page and `/quality/`

`src/pages/index.astro` and `src/pages/quality.astro` are hand-built Astro pages, not
content-collection entries, so none of the above applies to them: Starlight's i18n does not
route them and the `sourceHash` guard does not see them. **They are English-only today.**
Localising them means either extracting their copy into a per-locale dictionary module and
rendering both from one component, or duplicating them under `src/pages/fr/` — the second is
cheap to write and guaranteed to drift, since nothing would hash-check it. If you do the
first, extend `check-translations.mjs` to cover the dictionary at the same time; do not ship
a second copy of a 440-line marketing page with no guard on it.
