Every previous report on this site was a label-scoped gate: the milestone’s own criteria ran, and the rest of the suite showed up as skipped lines covered by some other run. This one has no filter and no label. All eight areas below ran in a single session on one cluster — the platform preflight, then M0 through M6 in order — so each earlier milestone is here as a non-regression on the M6 codebase, not as a citation of an older run. The verdict line the suite prints states its own coverage, 82 of 82 checks (100% of the suite), precisely so a filtered run cannot present itself as a gate.

And there are no skips. That is new, and it is not cosmetic: the published M5 report carried 47 skipped lines and the M4 report one conditional skip, and this milestone found that the crucible’s own operator-readiness check had been self-skipping in every published run since M1, behind an escape hatch whose documentation gave the wrong value. The restore-fidelity gate that closes M6 was therefore written with no enable flag and no conditional skip at all — a gate that can disable itself reads as a pass. A zero in the Skipped column is the claim being made here; the 82 is what backs it.

What the campaign surfaced

Three correctness defects, found by pointing the new instrumentation at the product

Running this campaign is what found them — the first in code that shipped in M1, the other two only visible with a real Prometheus scraping a real operator. Brief here on purpose — the full accounting, including what each fix does not do, is in the CHANGELOG.

product

A run reported success for data it never wrote

The worst class a backup tool can have, and M1 code: a Completed run with succeeded counts, for a volume whose bytes never landed. The restore-fidelity gate found it on its first real run, which is the entire argument for building the gate.

product

The ServiceMonitor overwrote every tenant’s namespace label

With honorLabels at its default, the target wins the collision — so every series arrived labelled with the operator’s namespace. Alerts still joined and still fired, then named the wrong namespace and routed every tenant’s page to one place. It took a real Prometheus scraping a real operator to see it.

product

An alert that could not page a first failure

A counter child is created by its first increment, so it appears at 1 rather than stepping 0 → 1, and increase() measures a rise. The first failure a series ever recorded could never move the rule — precisely the incident an operator most wants paged.

What this report does not say

82 green checks are not a production-readiness claim

v0.6.0 is offered for testing in real conditions by early adopters, not for production. The suite above is evidence that the code does what the checks describe on one cluster, for the duration of one run. It is not evidence of the things M6’s own exit criteria ask for, and those are not met:

  • The two-week soak alongside Velero on a staging cluster has not happened. It runs on a real build cluster after this tag.
  • The pilot rollout has not happened. The milestone’s exit criteria call for a production rollout on a pilot cluster for pilot namespaces; this release predates it. Together with the soak, this is the main reason 0.6.0 is a testing release.
  • Several M6 roadmap items are deliberately undelivered and should not be read as covered: mover resources by operation type and the cache sizeLimit decision, the millions-of-files load test (and with it the restic-vs-rustic revisit), VSC ↔ RBD-image reconciliation with trash monitoring and the active pre-check, S3 RGW tuning, and the PodSecurity review.
  • A green run is a sample, not a proof. Timing-dependent defects in this project have historically appeared roughly one run in three — which is why M4 was accepted on seven independent lanes rather than one. This is a single session.

Run it on a cluster whose loss you can absorb, alongside — not instead of — whatever you back up with today.
