The fields had been there the whole time. JobRequest.Resources existed and no caller ever assigned it; JobRequest.GoMemLimit existed, was consumed by the mover’s environment builder, was covered by unit tests, and no caller ever assigned that either — while the roadmap listed GOMEMLIMIT among what the mover shipped in M1. So 0.6.1 is not a release that tuned the numbers. There were no numbers. BestEffort is the bottom of the kubelet’s eviction order — under node memory pressure a running backup is killed before almost anything else — and an uncapped emptyDir lets one restic cache fill a node’s disk and take the node’s other tenants with it.

What follows is the same 82 checks as the 0.6.0 report, run for a different reason. Every mover pod in this campaign carried requests, a memory limit and a bounded cache volume for the first time. The mover.profiles ConfigMap on the cluster was verified live to be {} — empty — so what ran is the built-in table, not an override fitted until a run went green. Across the two hours: zero evicted pods and zero OOM kills. That is the number to read here, and it is not a coincidence that it is reportable at all: this lot ships the MoverEvicted and MoverOOMKilled conditions precisely so a sizing mistake would be legible rather than appearing as a pod that vanished mid-backup. Neither fired. Ceph held HEALTH_OK with 3 of 3 OSDs for the duration.

One procedural note, because this project publishes those too: an earlier attempt at this same campaign was interrupted mid-run by an orchestration mistake on our side and reported FAIL. It had passed 47 of the 47 checks it managed to execute. Nothing from it is carried over or cited below — the run on this page is a clean re-run from the first check, on a cleaned cluster.

What this run was actually testing

Four sizing classes over thirteen operations

The defaults live in exactly one file and nowhere else: the chart carries no quantities at all, docs/MOVER-RESOURCES.md is generated from the same table the code reads with a CI target that fails when the two drift, and the operator logs its effective table at startup. A quantity written twice is a quantity that will eventually disagree with itself.

Class Operations Requests (cpu / mem) Memory limit GOMEMLIMIT
data backup, restore 200m / 256Mi 4Gi 3276MiB
repo-heavy prune, check, sync 500m / 1Gi 8Gi 6553MiB
repo-light init, forget, snapshots, unlock 50m / 128Mi 1Gi 819MiB
manifests the four manifest operations 100m / 256Mi 2Gi 1638MiB

No class sets a CPU limit, and that is a decision rather than an omission. CPU is compressible: a mover that wants more than its share gets throttled by the scheduler, whereas a hard CPU limit on a backup buys nothing but a slower backup and a window that closes before the run finishes.

The restic cache sizeLimit is 20Gi, the same for all four classes. It is a ceiling against a runaway, not a fitted estimate: the cache is cold on every run — each mover gets a fresh emptyDir — so the cap bounds what one operation downloads rather than an accumulation, which is what makes a generous number defensible without the benchmark that is missing.

GOMEMLIMIT is derived, never configured: 80% of the operation’s own memory limit, floored to whole MiB, omitted entirely when there is no memory limit to derive from, or when the result would fall below 256Mi. The remaining fifth is not slack — it covers what the Go runtime’s accounting does not.

Requests are a scheduling floor multiplied by maxConcurrentMovers, not a reservation; limits exist to stop one runaway mover from taking a node down, not to right-size restic. Raise them if your repositories are large. Do not read them as measurements — see the panel at the bottom of this page.

What this report does not say

82 green checks do not make these the right numbers

v0.6.1 is offered for testing in real conditions by early adopters, not for production. The suite above is evidence that the code does what the checks describe, on one cluster, for the duration of one run, under this sizing. It is not evidence of the following — and the following are, plainly, not true yet:

  • The green does not prove the numbers are optimal. It proves they did not break anything this suite exercises. Not one of the 82 checks measures a mover’s peak memory or its cache high-water mark; they assert outcomes. A ceiling that is never approached and a ceiling that is correct look identical from a passing run.
  • The load test did not ship, and it is the one that matters here. The millions-of-files load test — the M6 item that would turn these conservative ceilings into measured values, and with it the restic-vs-rustic revisit — is still open. It needs infrastructure this campaign did not have. Until it runs, the table above is a set of defensible guesses with an override mechanism attached.
  • The two-week soak alongside an incumbent tool has not happened, and neither has the pilot rollout. Both are M6’s own exit criteria; both are still unmet. That is the honest reason 0.6.1 is a testing release rather than a production one, and it did not change with this campaign.
  • Other M6 roadmap items remain deliberately undelivered and should not be read as covered by a full-suite green: VSC ↔ RBD-image reconciliation with trash monitoring and the active pre-check, S3 RGW tuning, and the PodSecurity review.
  • A green run is a sample, not a proof. Timing-dependent defects in this project have historically appeared roughly one run in three — which is why M4 was accepted on seven independent lanes rather than one. This is a single session, and the sizing it exercised has been in existence for one of them.

Run it on a cluster whose loss you can absorb, alongside — not instead of — whatever you back up with today. If a mover in your installation is evicted or OOM-killed, the failure now arrives as a condition with the kubelet’s own message in it, and mover.profiles is the per-operation override that answers it.
