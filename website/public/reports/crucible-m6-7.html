Crystal Backup · Crucible acceptance

0.6.7 — Nine days of a report condemning volumes it was never allowed to look at

The release itself came out of a fortnight’s soak on somebody’s real cluster, exported and read: a self-check that spent nine consecutive days reporting 30 of 30 volumes as un-backupable while 28 of them completed every night, a customer’s PVC name in an exported Event that the redactor could not have learned, and a run that called 32 namespaces blocked without ever saying why. But the part of this cycle worth a reader’s attention is what happened after the code was written: nine campaigns, six of them red, three of them green, and not one of the reds was the product. No product code changed between several of them and the same digests were deployed each time. The verdict is 93 of 93 checks, unfiltered, in 2h40m25s — and two earlier 93-of-93 campaigns from this same cycle are deliberately not the verdict. The first validated a tree the release’s own security gates then refused over seven reachable advisories. The second validated a tree whose mover and sync still carried the unpatched restic and rclone — a real green describing images that would never be published.

Every finding in this release has one shape: an artefact reporting a fact when all it had was a refusal, a blind spot, a discarded string, or a bound it could not reach. A self-check whose read came back Forbidden and recorded the refusal as a fact about the storage. A redactor asked to substitute an identifier it had never been told existed. A classifier that computed the right answer and threw away the reason on the way out. And — this is the campaign’s half — a leak check that failed in 0.272 seconds on an object it had produced itself, and another that waited the full ten minutes for a backstop whose floor is forty.

Context, not measurement: not one of the three product findings was found by this campaign. All three came out of a soak archive from a cluster this suite has never touched. What the campaign contributes is narrower, and it is the only thing the 93 above is entitled to say: that the release containing those fixes still does, on real storage and a real object store, everything the previous ones did. Read it as a non-regression gate first. What is unusual this time is that the campaign itself became a subject of the release: nine campaigns were run and four went red without a line of product code changing between them, and every one of those reds turned out to be an instrument reporting something other than what it was pointed at. So did the sixth finding, which is not a campaign at all: a scanner that attributed seven advisories to a binary it never read. That is the same defect the three product fixes remove, found in the thing doing the measuring — which is why the campaigns are reported below as findings rather than as attempts.

What the soak found

The self-check spent nine days condemning volumes that were being backed up every night

The resident collector’s daily self-check reported 30 of 30 PVCs as ExposerUnresolvable, under a headline saying they would NOT be backed up, on nine consecutive days — while 28 of those volumes completed successfully every one of those nights. Every number in the report was arithmetically correct and its meaning was false.

The cause is one missing line of RBAC. Since 0.6.5 the exposer resolves a bound PVC’s driver from its PersistentVolume, because a StorageClass can be deleted and re-created under the same name with a different provisioner; the collector’s ClusterRole was never extended to match, so the read came back Forbidden and the refusal was recorded as a fact about the storage. The grant is added — along with storageclasses, a second gap found on the way, which a comment in that same file had explicitly struck off as “never read by internal/selfcheck” while the census had been listing them for unbound PVCs all along.

The grant is the smaller half. Any cluster that denies that permission — a restricted policy, a namespaced install — would have gone on reading the same false headline. So a refused or failed read now has its own class, ExposerUndetermined, and is kept out of the count of volumes that will not be backed up. The line is did the apiserver answer: a NotFound or a NoMatch is a real finding about the storage, a Forbidden or a timeout is a finding about the observer. The same conflation was found and closed in two more places — a refused VolumeSnapshotClass list was rendering “nothing in this cluster can be backed up” on every row, and a refused schedule list made every PVC fall through to “selected by NO schedule”.

What keeps it closed is not the fix. The reads the self-check performs are now declared in one place that both the code and a chart test consume, so adding a read without extending the role fails a gate on the maintainer’s machine. Writing that declaration immediately found a read no hand-audit had seen: the self-check reaches ClusterErasure through the alert predicate evaluated over its own reader. An audit done once, by hand, against code that then changes is worth nothing — which is exactly how the missing grant shipped.

What the reader should not conclude. No lane in this campaign runs the resident collector or its daily self-check, and no lane runs anything under a deliberately restricted role. ExposerUndetermined is covered by unit tests and by the archive that produced the incident; it is unmeasured on this page.

The second thing the archive said

An identifier the redactor could not have learned

The soak archive’s leak check failed: a customer’s PVC name appeared verbatim in an exported Event. The free text around it was properly redacted — the run name and the namespace in the same sentence came out as tokens — which is what made the cause worth finding rather than patching. The PVC had never been registered. PVC names entered the redactor only through a metric label that exists once a volume has a VolumeSnapshot, and the volumes a schedule complains about by name are precisely the ones stuck before they ever get one. The class was structurally invisible to the redactor, and no amount of care in the substitution pass could have covered it.

Both obvious fixes are wrong, and are rejected in comments. Removing the name from the Event destroys its only diagnostic value, on the administrator’s own cluster, where their PVC name is not a secret from them. Substituting every known identifier inside free text is worse: on the cluster that produced this archive the PVCs are named data and backups, so a blind pass would rewrite the English word “data” and the CRD plural backups.crystalbackup.io throughout, mangling the stream while still not being complete.

So the rule is bounded instead: identifiers we control are written quoted at the source, and the exporter substitutes only quoted exact matches of identifiers it knows, through a second registry the general free-text pass never sees. A PVC literally named data is tokenised where it is quoted and left alone in prose, and a test says so in those words. The convention was already half-present — both ConcurrencySkip emitters quote the previous run’s name with %q, which is why the run came out tokenised in the leaking message and the PVC beside it did not.

Two claims the leak disproved are corrected rather than deleted: manifest.go and the soak kit’s SPEC both asserted that every PVC name had been substituted out of the archive. What is deliberately not covered is stated where the rule lives — free text written by third parties, which is not quoted and reconstructs identifiers of its own. That larger piece of work is named at the bottom of this page, not in this release.

The third, and the smallest diff in the release

The run now says why it blocked a namespace, and that is all it does

Ten nights out of ten, on the same cluster, every ClusterBackup came back PartiallyFailed with namespacesBlocked: 32 while its namespace-level children were Completed and 28 of 29 volumes were backed up. The backlog entry this belongs to says the trigger is an unenumerated set and that the first job is to find the other paths — so nothing classificatory was changed here. No branch, no window, no guard: the diff over classifyCoordinate’s decision lines touches only its second return value.

Reading what that return value discarded is the finding. All four foreign branches rendered one reason and differed only in prose, so nothing was countable or greppable. The prose named each branch’s conclusion, never the facts behind it. And the run object’s creationTimestamp — the quantity the backlog’s own candidate fix turns on — was not a parameter of the function at all, so no volume of production evidence could ever have confirmed or refuted that hypothesis.

ClusterBackupStatus.blockedReasons now groups blocked namespaces by cause, with namespaces, withDataAtCoordinate and stampedByThisRun. Keying by cause is what keeps it bounded — five codes, whatever the estate size — where the ten-entry failure list could only sample 10 of 32, and where a per-namespace map is what adr/0009 refuses. stampedByThisRun turns the falsified hypothesis into a measurement: it counts coordinates the run itself demonstrably created and the fan-out still refused.

On the way, the shape this release exists to remove was found already present: the fan-out emitted one Warning per blocked namespace per reconcile — thirty-two a pass — evicting the rest of that namespace’s events well inside the hour they live. It is one Event per pass now, carrying the count and the breakdown. What the reader should not conclude: this is a new optional status field and one fewer Event, verified by unit and envtest coverage; no lane here reproduces a 32-namespace estate blocking ten nights running.

The gate that refused the release

Seven advisories reachable from the operator, and the canary had failed four hours earlier with nobody watching

The first 0.6.7 tag built cleanly and then stopped at its own security gates. govulncheck reported seven advisories reachable from the operator, and the trivy 0-known-CVE gate refused the mover and the sync images. All seven are in the Go standard library — net/url, net/http, crypto/tls, encoding/asn1, encoding/xml, html/template — and all seven are fixed in go1.26.6.

The scheduled vex-refresh had failed four hours earlier on the same wave. It was the canary, and nobody was watching it — which is the previous release’s subject arriving one release later in a different costume. A reachable advisory is a bug to fix, not a statement to publish, so this is a toolchain bump rather than a VEX entry, applied at the four places the version is pinned: go.mod’s toolchain directive, mise.toml, and the GO_VERSION of both workflows. Two comments in mise.toml quoted the old number and were corrected with it — a comment that names a version is a claim, and this one would have been false for the next reader.

Verified rather than assumed: govulncheck against both binaries now exits 0 with No vulnerabilities found, where the operator was affected by seven. The two imported and one required advisories it still lists are unreachable and remain the VEX pipeline’s business.

This is why the first of the two earlier greens is not the verdict. A full 93-of-93 campaign had already passed in this cycle, on the go1.26.5 tree — the tree these seven advisories then disqualified. Keeping a number that describes a tree nobody will install is exactly the defect this release spent three lots removing from the product, so that campaign is recorded here and is not the headline. And this was not the last refusal. The same workflow refused the tag a second time, on the same seven advisories and for a reason nobody had guessed — finding 6 below. The verdict at the top of this page was measured against the three digests below, and against nothing else.

The suite delta

The same 93 checks, name for name — and 26 files of harness changed underneath them

Measured, not assumed, and in both directions. No check was added and none was removed: the 93 check names in this run are identical, name for name, to the 93 the previous release was accepted on. That is what makes a green run a comparison against a known result rather than a fresh set of assertions written after the fixes they bless.

And underneath those unchanged names, the harness moved a great deal: 26 files under test/crucible/, 894 insertions against 279 deletions, none of it product code — against exactly one file and 21 insertions in the previous release. A leak-check predicate that now discriminates by ownership and has unit tests of its own on a file carrying no crucible tag, so make test exercises it without a cluster; a shared location promoted to a suite-level precondition with six deletions removed; per-case initialisation budgets; a wait that measures itself; and two crash-path budgets raised with the arithmetic written at the constant. Every one of those changes was bought by a red campaign, and each is described below.

What the reader should not conclude. A suite that changed this much under fixed check names is not automatically stronger. Three of these changes make the suite more patient — and patience can hide a regression as easily as it can tolerate a cold cache. That is why each raised bound below carries its measurement rather than a round number, and why the ones deliberately left tight are named too: sixteen of the eighteen leak-check call sites keep the short bound, because on a live operator prompt teardown is exactly what should be asserted.

How this campaign behaved

Nine campaigns, six red, three green — and not one of the reds was the product

This section is a standing part of these reports and it is not decoration. A campaign re-run until it is green and then published as if it had been green the first time is the exact dishonesty this project keeps finding in its own artefacts and removing. 0.6.4 published a campaign killed mid-run with no verdict. 0.6.5 published a red first attempt in which 21 of its 93 checks never ran. 0.6.6 published a red run whose single failure was a harness bound with no margin. This time there were nine campaigns, several of them with no product change between them — the same digests deployed each time — and the reds are the most useful thing the cycle produced. Two of the three greens are here for the same reason the reds are: a green campaign that describes a tree the release then refused to publish is a number about nothing, and dropping it would be the tidier of the two lies.

The seed stays unpinned, deliberately. Ginkgo shuffles top-level containers on every run and this suite pins no seed. The shuffle is the only instrument the suite has for finding cross-container coupling, and it has now found two real defects a fixed seed would have frozen into permanent green. Ginkgo prints the seed it chose, so a specific failure can still be replayed. That is also why the groups below are in a different order from the previous report’s: this is the order this run’s shuffle chose.

Finding 1 — run 1

A leak check that failed in 0.272 seconds, on an object its own run had just made

The leak check fails fast on residue that predates it, on the premise that “no teardown this spec is waiting on can remove an object that already existed before the spec looked”. That premise is false for a spec whose subject is a thirty-minute deadline: its own run’s clone PVC is necessarily older than its own leak check, and the teardown cannot even begin until the node plugin is restored three lines earlier.

The operator’s log settles it, to the second. The run went terminal at 23:36:08Z; the teardown sweep logged “exposure residue still draining; re-verifying” in the same second; the check entered at 23:36:09Z and gave the whole thing 0.272s. Nothing was leaking. The teardown had started and was told it was too late.

The discriminator is now ownership rather than age: residue attributed to a run this spec owns is polled within the existing budget, residue naming another run still fails fast — which is 0.6.5’s lesson about not absorbing somebody else’s leak, and it must not be lost. All thirteen call sites name their runs; none needed an escape hatch. 0.6.6’s green on that check was luck, not a verdict.

And this fix is what made finding 5 legible. Before it, the VolumeSnapshotContent that exposed the unreachable backstop would have been dismissed in under a second as another lane’s leak. The suite would have gone red, on the wrong reason, and the reaper would have stayed unexercised for another release.

Finding 2 — run 2

A lane waited ten minutes for a repository that six other sites kept deleting

The second red was a lane waiting ten minutes for the BackupRepository behind the shared dr location. The proximate cause is the shuffle: whether that lane found the location already created was decided by the run’s seed. Raising the bound would have made the symptom go away.

Fixing it properly found the larger half. dr was not merely created late — it was being deleted mid-suite by six sites. One lane’s BeforeAll deleted and recreated it for a “clean slate” it never needed, and deleting a location garbage-collects the very BackupRepository the other lanes poll for. The location is a suite-level precondition now, with one canonical bootstrap; all six deletions are gone; and the default-flag disagreement hiding behind them — four lanes creating it true, one false, each guarded by IsNotFound so the shuffle decided which won — is no longer expressible, the flag being a const with no parameter to pass.

Three ordering assumptions were found and deliberately left, with the reasoning recorded where they live: two lanes mutate the shared location’s spec and restore it in cleanup, which is correct only while the suite is serial and both cleanups run; the whole ensure/idempotent design assumes serial execution; and the leak predicate now lives in a file carrying no crucible tag, so make test exercises it without a cluster. Naming an assumption is not closing it, and these are named rather than closed.

Finding 3 — runs 4 and 6

Eleven minutes to initialise the first repository on a cold cluster, and about 637 of those seconds were an image pull

Two campaigns on two independently provisioned clusters died on the same 600-second bound, and the second measurement is what turned a hypothesis into a figure. The shared dr location was created at 07:29:56Z and reported Initialized at 07:41:04Z — 11m08s, missing the budget by 68 seconds. On the next cluster: 11m02s. Six seconds apart on two clusters is not variance.

The decomposition is the finding. In the same campaign every later repository initialised without trouble, and a probe on a warm cluster measured a fresh one at 31 seconds. So the ~637-second difference is neither provisioning nor the object store: restic init runs in a Job built from the mover image, which carries restic and rclone, and on a node with an empty cache that Job cannot start until the pull finishes. And it is paid once per node, not once per cluster — pullPolicy: IfNotPresent against three workers, so dr’s init warms exactly one of them and the first real backup schedules movers onto the other two, each paying the pull again.

This cycle’s own fix made it worse, and the comment says so. Promoting dr to a BeforeSuite precondition — the fix for finding 2 — is right for ordering, and it moved the first initialisation to the coldest possible moment. The budget is per-case now rather than one number: 10 minutes for every isolated repository, 20 for the shared one, with the rule proved rather than assumed, since BeforeSuite runs before any spec and dr’s init is therefore necessarily the cluster’s first. 20 rather than 15 is argued on the variable term: 1200s leaves 1.8× the measured pull, enough for one ImagePullBackOff retry or a registry at half bandwidth, where 900s leaves 1.36× — the same knife’s edge that lost 0.6.6 by 462ms and 0.6.7 by 68s.

The part that matters is that the wait now measures itself. It reports its elapsed time on success as well as failure, from a defer so a timeout cannot skip it, and the failure message states the elapsed time, whether any repository had initialised at entry, and that a third raise would mean the pull is not the explanation. Reconstructing this number after the fact was nearly impossible: the Events had expired and the operator pod had been recreated by a lane that kills it deliberately. The survey that came with it raised the next bound it found exposed — m6/headline’s ten-minute wait for the first real backup, where ten minutes was the pull alone — and named the rest at the bottom of this page instead of raising them speculatively.

Finding 4 — run 5

A campaign disqualified by an operator error, published as a disqualification

Run 5 is not a red run. It is not a result at all, and the reason it appears on this page is that a campaign quietly dropped is indistinguishable, later, from a campaign that never happened.

It was relaunched on a cluster that still carried a deliberately corrupted repository — and its looping check Job — left behind by an aborted lane of run 4. The very next lane asserts that the critical alert fires “only for the damaged repository”. There were two. No assertion written that way can survive it, and no verdict from that cluster means anything.

The mistake underneath is worth more than the incident. The check for product residue — PVCs, VolumeSnapshots, VolumeSnapshotContents — had come back empty, and empty was read as clean. It was not: the corruption lived in the object store and in a Job, neither of which that check looks at. Cleanliness of a cluster is not the absence of product residue, and the leak-check invariant this suite is built around answers a narrower question than the one an operator relaunching a campaign is actually asking.

What the reader should not conclude. Nothing about the product is established or impugned by run 5. It is here because the rule these reports follow is that every campaign behind a verdict is accounted for, and the rule has no exception for the embarrassing case — the same reason 0.6.6 published a red run whose failure was in the suite.

Finding 5 — run 7

A backstop no campaign could reach, which means nobody had ever verified it

Run 7 failed one check: the crash-restart spec’s leak invariant, after polling its own run’s residue for the full 600s. The message the ownership fix now produces named the object exactly — a VolumeSnapshotContent with deletionTimestamp <nil> and ownerRefs []. Nothing had asked for its deletion and nothing would collect it but the orphan reaper.

And the reaper cannot be observed inside ten minutes. Its floor is MinAge 30m and Interval 10m, so an orphan is eligible at creation + 30m and swept no later than +40m — the sweep just before eligibility misses it. The arithmetic of that run: the object was created at 21:26:10, the check entered at 21:31:16 and gave up at 21:41:16, roughly twenty-five minutes before the object became eligible for the only mechanism that would ever collect it.

So the finding is not the timeout. The spec was green only when the ordinary teardown won the race. Until this release, every past pass of that spec was a run in which the reaper was never exercised at all — which means the backstop the crash path depends on had never once been verified by any campaign, ever. A timeout is a slow test. A backstop no campaign can reach is a backstop nobody has verified, and the two are only distinguishable because the run-1 fix made the object’s ownership legible instead of dismissing it in 0.272 seconds.

0.6.7 bought the observation with patience, and the comment carries the arithmetic rather than a round number: 50 minutes = 30m eligibility floor + one 10m interval for a sweep that just missed + 10m for the sweep’s own delete and read-back plus the external snapshot-controller’s Delete-policy cascade, measured at just over five minutes under load. 45m was rejected for landing exactly on the worst case plus that cascade. Sixteen of the eighteen call sites keep the tight bound; the two that move are the two on a kill path, and what they now assert is weaker and truer: not teardown is prompt, but that a crashed operator loses nothing permanently. A failure there is now a real permanent leak.

The cost, stated rather than buried. That is up to 100 minutes of additional waiting available to a suite that has measured 2h50m16s green and 3h10m55s red, so a pathological run now lands between roughly four and a half and five hours against the 330-minute timeout in the harness — inside the ceiling, with less headroom than any other raise in this suite has left. On this campaign it cost nothing: the crash-path check finished in 5m40.1s. Which is also the honest reading of it — the ordinary teardown won again, so the reaper still has not been exercised. The budget is patience held in reserve; the assertion that would actually exercise the backstop is a product change, and it is at the bottom of this page.

Finding 6 — the second refusal

The scanner was right, the first diagnosis was wrong, and it had never read the binary

The images workflow refused the tag twice. The first refusal is the section above: seven advisories reachable from the operator, closed by go1.26.6. The second came after that bump, and it named the same seven — this time attributed by trivy to restic 0.19.1-r0 inside the mover. This is the most instructive finding of the release, because the obvious reading of it was wrong.

The obvious reading was “melange builds restic with go-1.25, so the CVEs really are in that binary”. Trivy never read the binary. Its own output says language-specific files num=0. It compares the apk’s name and version against the Wolfi security database, which records the fix at restic 0.19.1-r3 — and our package was calling itself -r0. The scanner was making a claim about a version string, and it was correct about the version string.

So the fix needs both halves, and neither alone is acceptable. The patched toolchain is what makes the claim true: go-1.25 stops at 1.25.12 in Wolfi, the backport that closes these landed in 1.25.13, and with Go 1.25 end-of-life it is never coming — so the recipes move to go-1.26, which Wolfi ships at 1.26.7. The epoch bump is what makes it visible to the scanner. Bumping the epoch alone would have been a lie that silences a scanner, which is precisely the suppression spec/adr/0013 refused once already, in the rule both recipes now carry in capitals: the epoch is load-bearing. It is a claim, not a counter. Wolfi’s later -r4 and -r5 record no security fixes, so -r3 is the smallest honest number rather than the highest available one.

rclone could not be fixed by an epoch at all. apk orders 1.74.4-r99 below 1.75.0-r1, and Wolfi records the standard-library batch against 1.75.0 — so no epoch on the 1.74.4 line could ever have cleared it. The recipe therefore followed the policy already written in it and tracked the newest upstream release. Two overrides were dropped because they had become false: 1.75.0 pins x/text and grpc past the versions this build was forcing, and going on forcing them would assert a difference the binary no longer makes. One was added — x/image v0.45.0 for CVE-2026-46603, which 1.75.0 still carries at 0.44.0 — and that addition is what makes the epoch -r2 honest rather than -r1.

Verified with a control rather than by watching the gate go green. Scanned locally, both ways: the old pins report 16 findings across all severities, the new ones report 0 and 0, exit 0 — not merely zero above the gate’s CRITICAL,HIGH threshold. A gate that passes because the finding moved below its threshold is the artefact this whole page is about, so the control was run at every severity on purpose.

The whole suite follows, in the order and grouping the run reported it. Check names and durations are reproduced verbatim — including the ones that read 0s, which are separate verdicts on one measurement rather than checks that did nothing. The order within each group is the order this run’s shuffle chose, and it differs from the previous report’s on purpose: the seed is not pinned. Repository assertions still go through an independent restic oracle, a throwaway Job running the plain restic CLI, so a controller that both writes and reports the same wrong thing cannot make a check pass. Durations are not comparable between campaigns: several of these lanes wait out a real deadline, and one re-reads a repository whose size depends on everything that ran before it.

What this report does not say

Three fixes found outside this suite, one backstop still unexercised, and a page whose own subject is instruments that overclaim

v0.6.7 is offered for testing in real conditions by early adopters, not for production. Everything below is still true after 93 green checks, and a report whose subject is artefacts that report more than they measured has a particular obligation not to be one:

  • Not one of these 93 checks was written to test anything this release fixed. The 93 names are identical to the previous release’s, which is precisely what makes the run a clean non-regression comparison — and precisely why a green gate composed entirely of older assertions can only tell you that the fixes broke nothing it already watched.
  • All three product findings came from a soak archive on a cluster this suite has never touched. The self-check RBAC gap, the unregistered PVC name and the discarded blocked-namespace reason were found by exporting a fortnight of a real cluster and reading it. No lane here runs the resident collector, exports an archive, or runs anything under a restricted role, so ExposerUndetermined, the quoted-match redaction rule and blockedReasons are all covered by unit and envtest coverage, not by anything on this page.
  • The orphan reaper is still not exercised. This is the uncomfortable one. The crash-path specs now have fifty minutes of patience, and on this campaign they used 5m40.1s and 1m9.5s of it — meaning the ordinary teardown won again and the backstop did not run. The specs can now survive the case where it must; they still cannot distinguish “the reaper collected it” from “the reaper would have, eventually”. That distinction needs a product change, named below.
  • The security gates are CI’s measurement, not this one. govulncheck and the trivy 0-known-CVE gate run on a different surface.   • Three of the raised bounds make the suite more patient, and patience is not evidence. A cold-start cost tolerated at 20 minutes and a backstop tolerated at 50 would each also tolerate a genuine regression of the same size. Each carries its measurement at the constant, and the fix that would remove the need for both is a product change and a provisioning change, not a third raise.
  • No lane in this campaign drives a hook chain on real infrastructure, unchanged from the previous two reports. The two hook-chain defects 0.6.6 closed remain covered by unit and envtest coverage only.
  • A green run is a sample, not a proof. Timing-dependent defects in this project have historically appeared roughly one run in three, which is why M4 was accepted on seven independent lanes rather than one. What this cycle hands to M7

Four entries, each with its measurement attached, and the first one buys back forty minutes of waiting

Expose the orphan reaper’s cadence. MinAge and Interval are struct fields whose defaults Start applies, so the product is one step from configurable — and nothing exposes them: no CLI flag, no Helm value. A flag, a Helm value and defaulting on those two fields would let a crash-path spec set MinAge to a minute and assert the collection in minutes instead of tolerating forty, giving that wall clock back. Two alternatives are rejected in writing. Leaving it test-side and living with the 50-minute budget buys the assertion but never the backstop. And shortening the production defaults trades away what the 30-minute floor exists to be — a race guard, since a temp clone PVC or mover Job can exist for a few reconciles before the owning Backup’s status catches up, and reaping one out from under a slow-but-live reconcile corrupts an in-flight backup.

Pre-pull the mover image at provisioning time, so that no test bound carries it and the cost is paid once, visibly, during provisioning. The honest counter-argument belongs with the work rather than after it: a pre-pull hides a genuine first-pull regression from every campaign — a mover image that doubled in size, or a registry serving at a quarter of the bandwidth, would stop being observable anywhere. So whatever does the pre-pull must report its duration into somewhere a campaign actually reads, in the same spirit as the self-measuring wait this release added. The bounds still exposed are named with it rather than raised on suspicion: m6/precheck’s two ten-minute run waits, the six fifteen-minute run waits which leave about 4.4 minutes of real backup after a cold pull, and the sync image — a third image no mover ever warms.

Triage leak-check hits by provenance instead of grepping the archive verbatim. The soak collector searches the unpacked archive for every namespace, PVC, location and bucket name of the cluster, verbatim — and on the cluster that produced this archive the PVCs are named data and backups, so it reports the CRD plural and an English word as leaks: 92 hits in the log stream alone, every one of that shape, forever, on every export from that cluster. A check that always fails is a check nobody reads, which is the same defect class 0.6.x has spent twelve lots removing. Three classes have to be separated: the product’s own vocabulary (a false positive), third-party free text that reconstructs an identifier without quoting it (a real exposure the shipped rule does not reach), and a genuine leak in a field that should have been tokenised (the only one that is a defect). The residual this release deliberately left is recorded with it, because narrowing it would regress a documented guarantee of the self-check report — whoever takes that entry decides both halves at once or neither.

And one entry stated as a question rather than a design: nothing durable records the timings that decide an attribution. This cycle hit that twice and answered it neither time. When a campaign or a soak window fails, the evidence needed to say why is gone within the hour — Events have expired and the operator pod has been recreated, routinely, because several lanes kill it deliberately. Both times the timings could only be reconstructed from status.conditions[].lastTransitionTime, which happened to be enough once (07:29:56Z created against 07:41:04Z Initialized) and impossible the other time, where the question was what the dying operator had and had not managed to record. Not more logging — the logs were written, and then the pod holding them was replaced. The question is what the smallest durable, bounded record of those few timings is, and who writes it; the mistake to avoid is the one the soak kit already made once, which is building the instrument before stating what it must be able to answer.
