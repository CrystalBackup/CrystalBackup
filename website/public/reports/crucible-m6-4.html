0.6.4 — The fix was wrong twice before it was right

0.6.3 shipped in the evening. Before midnight an Argo CD prune deleted the operator namespace on a real cluster, and the operator minted a fresh key over the only one that could open a repository holding 38 snapshots. The fix that stops it took three campaigns: one killed mid-run with no verdict, one that went 87 / 1 / 2 because the first cut of the guard over-applied its own invariant, and this one. 90 of 90, unfiltered, against the exact operator digest v0.6.4 ships — and the suite is byte-identical to 0.6.3’s, so the check that caught the over-blocking was already sitting here.

The setup was mundane. An administrator lost the operator’s namespace to an Argo CD prune — the hazard 0.6.3’s own install page warns about, made live by 0.6.3 itself, which stopped rendering the Namespace object so a prune saw it as no longer wanted. They rebuilt the namespace and restored the cluster KEK from escrow. The S3 credentials arrived two minutes later. In those two minutes the operator started, found a ClusterBackupLocation that had survived because it is cluster-scoped, and began reconciling it. It could not read the credentials, so it could not read the bucket escrow, so it did not know whether a recoverable DEK existed — and it provisioned the repository anyway. EnsureDEK minted a fresh DEK four seconds after the KEK landed, and the location reported Ready for an hour while every mover failed wrong password or no key found against 38 snapshots. Only the escrow’s refusal to overwrite a bucket object it could not prove redundant kept that recoverable.

So the number that matters in this run is not 90, and it is not eight new checks either — this campaign added none. It is one duration: 17m11.2s, on increments the failure counter and pages, with no hold to wait out, which timed out at 300s in the previous attempt. That check is the only evidence separating a gate that refuses the right things from one that refuses too much, and it was written for 0.6.2’s alert work by somebody who had never heard of this defect.

What this run caught

The first cut of the fix over-blocked, and m6/alerts is what said so

The rule the release installs is an invariant rather than a list of cases: provisioning is allowed only where reconcileDEKEscrow has positively established that it is safe. Exactly two states qualify — an in-cluster DEK already exists, so EnsureDEK has nothing to mint; or there is provably no DEK anywhere, so minting is what should happen. Everything else blocks, including every failure to even ask the question.

The first cut applied that rule to a state it does not cover. EscrowUnreachable was made to block in both branches — including the one where an in-cluster DEK is already present. That contradicts the invariant directly: a DEK that exists is one of the two states where minting cannot happen. Nothing could fork, and provisioning was refused anyway.

The lane that failed is the one that breaks a location’s S3 credentials on purpose. m6/alerts drives a backup to fail by replacing the credentials with garbage — replaced, not deleted, because garbage credentials let the mover Job run and be rejected by the object store, which is the ordinary shape of a rotated key nobody updated. The credentials Secret still reads, so under the over-blocking the failure surfaced at Fetch instead: the location went Degraded, and the run started failing earlier than the mover — which took crystalbackup_backup_failures_total with it. An alert about failing backups could no longer see a failing backup. The campaign stopped 300 seconds into an assertion whose own message says what it means: the failure counter was never recorded.

So, and this is the sentence the release is built on: over-blocking is not erring on the safe side; it moves the outage. Here it moved it somewhere no rule was watching — the same shape as the thirty-six-hour stall 0.6.3 closed, where six mover pods sat in ContainerCreating and nothing was measuring the thing that had stopped.

And the correction needed a correction

One reason was carrying two opposite verdicts, three lines from where that defect was being fixed

Returning “do not block” from the local-DEK branch fixed the over-blocking and left EscrowUnreachable meaning two opposite things: you are fine in one branch and a recoverable key may be sitting in the bucket in the other. That is this release’s own defect — one name for two verdicts — reproduced three lines from where it was being fixed. Hence two names, because they say different things to the administrator reading them:

Reason The same underlying I/O failure, in two situations Blocks
EscrowUnverifiable the bucket could not be read, and an in-cluster DEK is present. EnsureDEK has nothing to mint, and Put is never reached — so a bucket this pass could not read cannot be overwritten by it. You are fine. no
EscrowUnreachable the bucket could not be read, and there is no local DEK. A recoverable key may be in there, and minting would fork the repository. yes

The lasting part is not the fourteen cases; it is the guard above them. A table of outcomes enumerates what exists today. The guard enumerates inputs, reads whichever reason each one lands on, and fails on any reason outside a small allow-list where every entry argues why minting cannot fork the repository. A return false copy-pasted into a branch added in two years fails there without anybody having written a case for it — which matters, because the original code was a correct list of cases whose rule had been inverted in most of them.

Before this release the escrow had no tests at all — on the code with the worst failure mode in the product. Everything else can lose a backup run; this can lose the ability to read a repository.

What was under test

Three images, and why two of them are the same as last time

Reusing an image digest across releases is the kind of claim that has to be checked rather than assumed — the previous release contained an incident in which a silenced build step reused a three-day-old package and published an image byte-identical to its predecessor’s, exiting 0. So: the operator image is new and is the one v0.6.4 ships. The mover and sync images are unchanged since v0.6.2.

What changed is what the operator decides; what executes a backup is the same binary.

Also

Three things worth recording about how this got found

None of the three is a product defect, and all three bear on how much the verdict at the top is worth.

unit test

A test in the same package had blessed the over-blocking

The row asserting the block carried a justification: the bucket may hold another generation’s key. True, and beside the point — that is about conflict detection, and it licenses nothing about minting. A green unit test agreeing with the code it was written beside is not independent evidence, which is why the invariant guard matters more than the table.

campaign 1 of 3

Killed mid-run, so it produced no verdict at all

The first campaign was interrupted mid-run. It is recorded here because a campaign with no verdict is neither a green one nor a red one, and a two-hour run that ends without a report is the easiest thing in this process to remember as having passed.

suite scope

The suite gained nothing this cycle, deliberately

git diff v0.6.3..HEAD -- test/crucible is empty: not one line of the suite changed. 0.6.3 added eight checks; 0.6.4 added zero. The lane that caught this release’s defect was already here — and the gap it does not cover is stated at the bottom of this page rather than closed by a check written after the fact.

What this report does not say

The release’s central change is a refusal to act, and no lane here drives it

v0.6.4 is offered for testing in real conditions by early adopters, not for production. Everything below is still true after 90 green checks, and this page would be easy to read as claiming otherwise:

  • No lane in this suite puts the escrow into an unresolved state on purpose. Nothing strips a location’s S3 credentials out from under a live operator. So this campaign proves the tightened gate did not break the working paths — which, after narrowing a guard, is exactly the risk worth measuring, and it is the risk that went red on the previous attempt. It says nothing about the behaviour under uncertainty. That rests on fourteen unit cases and an invariant guard, both against a stubbed S3. Read the verdict at the top as covering the first claim and not the second.
  • The two-week soak alongside an incumbent tool has not happened. Neither has the pilot rollout. Both are M6’s own exit criteria and both remain unmet. 0.6.2 built the instrument that would watch a soak and 0.6.3 fixed a version-attribution defect in it. Nobody has run the fortnight.
  • The defect this release fixes was found on a user’s cluster, not by this suite — for the second release running. It was found within hours of 0.6.3 shipping, by an administrator restoring a namespace, doing nothing exotic. Two releases in a row have been driven by findings this campaign could not reach.
  • The incident’s real first cause is not in this release at all. The namespace was deleted by a prune, and nothing in the chart stops that. upgrading.md now warns where an upgrader meets it, but a warning is documentation. A chart-side guard — an annotation that makes Argo CD refuse to prune the namespace it must not touch — changes how the chart is installed, and it was deliberately not designed at midnight in a patch release.
  • The escrow is not bulletproof; the operator now refuses to act while it does not know. An administrator who restores the wrong KEK still has an unreadable repository. 0.6.4’s contribution there is that it says so in a reason of its own — EscrowUnreadableUnderKEK, ClusterDEKUnreadableUnderKEK, EscrowConflict — instead of one sentence asserting a key comparison that, in two of the three cases, never happened.
  • A green run is a sample, not a proof. Timing-dependent defects in this project have historically appeared roughly one run in three, which is why M4 was accepted on seven independent lanes rather than one. This is a single session, and one of the three campaigns behind this release produced no verdict at all.
  • The PodSecurity review is partly executed, not done. The posture crystal-backup-system must carry is enforced by the chart in three places and checked by the operator at startup, but the review as a document is still unwritten.

Run it on a cluster whose loss you can absorb, alongside — not instead of — whatever you back up with today. Before installing, run preflight.sh and then snapshot-probe.sh: the first reports every resolvable storage class as USABILITY NOT ASSESSED, which is the honest answer, and the second is what actually answers it by snapshotting, restoring and mounting on your nodes. And restore both the KEK and the S3 credentials Secret before the operator starts — the ordering that produced this release.
