Crystal Backup · Crucible acceptance

0.6.6 — CI had been red for eight days, and looking for why found seven more

This release began as one complaint: “I get an error mail every time CI runs, even when every gate is green locally. For 0.6.6 I want it all clean.” The search for the cause became the release’s subject — a check that cannot fail is not a check — and the tree turned out to be full of them: two CI gates red on every push for eight days, an aborted quiesce that left applications frozen and said nothing, seven errored passes in the four controllers the previous release had never swept, two protections that had never once run, and a script that told administrators a storage class was fine when that class had never produced a single backup. 93 of 93 checks, unfiltered, in 2h50m16s — the same 93 as 0.6.5, because this release added no check and removed none. It took two attempts, and the first was red: 92 passed and one failed, on a test-harness wait bound with no margin, while the product it was waiting for had done the work in 462ms.

Every previous release on this page was driven by something breaking. This one was driven by something that never broke, ever, on purpose. A gate that fails on every push is not information; it is furniture, and everybody had learned to walk around it. That is the same defect as a counter nobody can believe, or a warning fired four times a minute for weeks, or a script that calls a storage class usable because a class object for its driver exists. In each case the artefact is present, green or loud on schedule, and carries no evidence either way. They were all found inside one release, and each of them has a section below.

Context, not measurement: not one of those stories was found by this campaign. They come from CI’s own build history, from two production clusters, from a static audit of five controllers, and from unit and envtest coverage written with each fix. What this campaign contributes is narrower, and it is the only thing the 93 above is entitled to say: that the release which contains all of it still does, on real storage and a real object store, everything the previous ones did. Read it as a non-regression gate first, and as proof of the new behaviour only where a lane actually drives it — which for several of these fixes is nowhere, stated plainly at the bottom of the page. This edition has one extra reason to insist on that distinction: the failure that made this a two-attempt campaign was in the measuring instrument, and a suite that can go red without the product having done anything wrong is worth exactly as much attention as a gate that cannot go red at all.

The measurement that started it

Lint 9 of its last 10 runs, unit tests 9 of 10, and three findings that cannot fail on a maintainer’s machine

The complaint was “CI is flaky”, which is a claim. 9-of-10 is a fact, and it was measured before anything was touched: on main, Lint had failed 9 of its last 10 runs and Unit tests 9 of 10, while Security, E2E, vex-refresh and the site deploy were all green. Both had failed on every push since 2026-08-03; the 08-02 run was the last green one. Not flakiness — a deterministic red that had been mistaken for noise for eight days.

Three findings, always the same three, and the property they share is the release’s subject: every one of them cannot fail on the maintainer’s machine.

  • internal/soak/freespace_unix.go, an unconvert finding. One //go:build unix file serves linux and darwin, and unix.Statfs_t.Bsize is int64 on the first and uint32 on the second — so the conversion is redundant on the runner and required locally. It is kept, with a nolint that says why, because the next reader deleting a “pointless” cast breaks the darwin build.
  • cmd/main.go, an SA1019: the last user of the old events API. Its ten siblings had already moved and this one was missed, so the field type and the Eventf signature moved with it rather than being suppressed — a deprecation that says will be removed is debt with a deadline, and silencing it converts a dated obligation into an undated one.
  • TestSoakCollectRefusesToStartBlind, which passed locally only because the machine has a kubeconfig. soak-collect validated the cluster connection before reading --redaction-salt-file, so on a runner it exits 1 about KUBERNETES_MASTER instead of 2 about the path the operator typo’d. A usage error must not depend on whether a cluster happens to answer.

And the reason all three hid. rm -f bin/golangci-lint rebuilds the linter but does not clear ~/.cache/golangci-lint, so a local make lint can report zero issues out of stale cached results while CI, cold, rejects the same tree. lint now purges the analysis cache by default — LINT_CACHE=keep opts out, and its comment says what that costs — and gained a GOOS=linux pass, because a darwin-only run structurally cannot see a linux-only finding inside a build-constrained file. That is the fix that generalises: the other two were single findings, this one was the blindfold.

What the reader should not conclude. Nothing on this page certifies CI. The 9-of-10 figures come from build history and the fixes are verified by CI going green, on a surface this campaign never touches. A green crucible and a green pipeline are two different measurements on two different machines, and this release exists because the third one — a green local make lint — had been quietly disagreeing with both.

What the search found next

An aborted quiesce left applications frozen, and said nothing

hooks.Run stops the chain at the first onError: Fail failure, which is correct. But the hooks that already succeeded have quiesced their applications — and failHooks then wrote a terminal Failed, which the already-terminal short-circuit turns into closeFreezeWindow never runs. Nothing thawed them and nothing said so. The run reported a reason that reads the quiesce did not work at the moment part of it had worked and was still in effect. R16’s own priority — the release matters more than the backup — inverted on the one path where nobody is looking.

What the fix guarantees. The release now runs before the termination, and the terminal write is held while a thaw is owed. Only Succeeded pre entries are thawed: a Skipped never ran, and a thaw against a pod nothing froze is a command its owner never asked for. It reuses the existing attempt budget and ends at the existing UnfreezeFailed Event rather than inventing a second one, and a new Ready reason names the abort and the attempt while it retries — which is the “nothing said so” half, and the half that costs an administrator an hour of guessing.

Two alternatives are rejected in comments, at the lines where they would have to be re-argued. Thawing then writing terminal in one pass would bar every retry, giving one attempt of three exactly where an application is most likely to be stuck. Thawing from ensureTerminalTeardown conflates two different owed-things: that sweep’s subject is storage residue, verified by reading the cluster and safe to repeat forever, whereas a thaw is an exec that must be attempt-bounded — and it would report Failed and thaw afterwards, which is precisely the dishonesty the hold exists to prevent.

The same lot fixed its mirror. A Fail-policy post-hook failure marked the rest of the chain Skipped, so a permanently broken first hook meant the later pods were never thawed across all three attempts — loud, via UnfreezeFailed, but about the wrong pod. Stopping the chain is right for the pre phase and wrong for the post phase, where every entry is a thaw owed to a different application. The rule is written phase != PhasePost so an unstamped or future phase fails closed.

What the reader should not conclude. These are the two hook-chain defects the 0.6.5 report listed as covered nowhere at all. They are fixed; the coverage gap is not. No lane in this campaign drives a hook chain on real infrastructure, so the verdict above says nothing about either path — see the bottom of the page.

The class 0.6.5 left open

Seven errored passes in three controllers, and zero in the fourth — shown, not asserted

0.6.5 closed the errored-pass class in the Backup controller and verified by two independent methods that none remained there. Four other controllers shared the shape and nobody had looked — which that release said in as many words rather than implying the rest were clean. The audit ran both methods again: control flow from each Reconcile’s first in-memory status mutation, and a mechanical classification of every error-carrying return. The two agreed everywhere. ClusterErasure has zero instances — shown by classification, not asserted. The other three had seven.

Two are worth naming for what they cost, because “a status write was skipped” sounds like bookkeeping until you see which sentence a human reads instead:

  • A clean restore, re-read as a possible failure. On the pass that reads the manifest apply’s report out of the mover pod’s termination message, that report was discarded — and readMoverResult reads the pod, with no annotation fallback. So once the pod is gone the re-derived verdict is “did not report a result … some resources may have been applied” with failedCount 1. A clean apply of an entire namespace, reported as maybe-broken, on the operation people run on their worst day. The manifest half now persists before propagating, and the volumes are driven on that pass instead of being held behind it.
  • A counter that would have said 0 instead of 4 of 6. When the pass cannot read the mover census no volume has a verdict, so the tally is empty — and publishing it would overwrite a real four-of-six with plannedVolumes: 0. Not a missing answer but a wrong one, in front of somebody deciding whether to abandon a restore. That pass now persists everything else, leaves the counters at their last published values, and says why in the condition.

The rule the sweep settled is that the shape depends on what the failing unit is: per-item failures are recorded and the pass continues; whole-object failures persist, then propagate. The Confirmed-condition sites are deliberately left as they are, because nothing about the restore’s work is lost there and the condition is a pure function of spec — and the trade is argued in code, at the line where it would have to be re-argued.

What the reader should not conclude. This is a static result, not a measured one. The seven instances were found by reading control flow and classifying returns; no lane in this campaign makes the apiserver refuse a status write at a chosen pass, so a green run cannot corroborate the sweep. What it can do — and what it is here for — is show that reordering writes in four controllers did not change any outcome the suite already pins.

Two protections that were never once used

A one-hour recheck that returned fifteen seconds, and a write that did not write

The recheck. ClusterErasure’s Immutable branch called park and then tried to override its Result — but park always answers a non-zero RequeueAfter, so the !res.IsZero() guard returned park’s 15 seconds every pass and erasureBlockedRecheck was dead code. Worse, the ErasureBlocked Warning sat before the park, so an erasure waiting out an object-lock emitted four Warnings a minute for weeks — on the most sensitive compliance path there is. An erasure record is the artefact somebody points at to assert data was destroyed; drowning it in its own noise is the surest way to hide the one that matters. One function now decides the cadence, and the Event fires on the transition.

The write. The external-sync controllers route every exit of Reconcile through one write helper — excellent single-writer discipline — whose first branch returned without writing whenever an error was present, under a doc comment promising “persists status once per reconcile”. There is no live defect today, and that is verified: the only non-nil errors reaching it come from two apiserver reads, both upstream of any status mutation. But it is a funnel for every exit, so its error branch is downstream-capable of everything, and the view aliases SnapshotsCopied, BytesCopied and LastSuccessTime — figures that are the result of work already done and are not recomputable.

Neither obvious fix was taken. Inverting to persist-then-propagate would spend a write on a pass whose only news is the apiserver would not answer, on exactly the path where writes are already failing — a trade the Restore controller argues against explicitly, and this release did not want to contradict its own reasoning one directory over. Keeping the skip behind a test that pins which paths may reach it guards a convention, and the next author adding an error return has no reason to read that test. So it persists only when the pass actually changed the status: structurally immune, and no write on today’s two paths, so the Restore argument keeps holding instead of being overridden. It fails toward persisting if a plane is ever mis-snapshotted — degrading to the merely wasteful option rather than to silent loss.

What the reader should not conclude. One of these two was a live defect for weeks and the other was never observed at all, and the campaign can see neither. No lane waits out an object-lock long enough to count Warnings, and no lane drives an external sync into a failing apiserver read. The write change is guaranteed by a structural property — a pass that changed nothing has nothing to lose — not by an observation on this page.

The other half of the release: prediction

A cluster that had never once backed up a CephFS volume, and a script that called that class perfectly usable

A production cluster had never once backed up a CephFS volume — not “stopped working”, never worked. Eight volumes across four namespaces, every one SnapshotReadyDeadlineExceeded, for as long as the cluster had existed. The cause was outside this product: the CephFS csi-snapshotter ran with a group-snapshot feature gate while the cluster’s CRDs served only the older API version, so its informer cache never synced and it never processed a single VolumeSnapshotContent.

The product’s verdict was exactly right and its Event said precisely where to look. What no artefact said was that this had never worked. And preflight.sh, whose entire job is to tell an administrator before installing what will and will not be backed up, called that class perfectly usable — because a VolumeSnapshotClass for the driver exists. A static predictor, predicting the wrong thing confidently. The information needed to be right was in the cluster the whole time.

What the fix guarantees. The symptom needs one LIST and no new permission: VolumeSnapshots bound to a content and still not ready past a grace period. It now appears on all three surfaces that had the information and were silent — the preflight script; selfcheck, beside leakIndicators, whose shape it mirrors; and as a qualification on 0.6.5’s per-PVC census, where a class of ok on a StorageClass that has never produced a ready snapshot is a prediction too confident to leave alone.

It is deliberately an observation, not a verdict: nothing becomes Skipped or Failed, no phase moves, and a class with no snapshots at all is not maligned — absence of evidence is not evidence of failure. A version-comparison check was rejected: it would need a third-party version catalogue and would go stale on every ceph-csi release, whereas the symptom catches causes nobody predicted — including this one, which no catalogue would have listed.

The one bound worth reading. The grace is one hour, and the binding constraint is a ceiling rather than a floor: at snapshotReadyDeadline (2h) the controller fails the volume and tears the origin VolumeSnapshot down, so a grace set near two hours would observe an empty window and be structurally blind to the operator’s own stalled snapshots. Being wrong here costs a sentence rather than a volume, so — unlike every other bound in this codebase — erring long is the dangerous direction.

What the reader should not conclude. The campaign’s cluster does not have this shape. Its snapshotters work, which is what the platform preflight group asserts, so no lane here produces a bound-and-never-ready snapshot on real storage and the new observation has nothing to report. That the observation is correct rests on unit coverage and on the incident it was written from; that it is silent when nothing is wrong is the part a green run here is evidence for.

The instrument

The soak collector had to survive its own upgrade, and strategy: Recreate did not save it

A GitOps autosync replaced the soak collector’s pod at the moment the fortnight’s archive was to be exported. The archive sat on a ReadWriteOnce volume the new pod could not map, so collect.sh answered NOT COLLECTED — with the data unreachable, on the volume the operator was about to delete. What saved the measurements was that somebody had read soak-export --status minutes earlier and transcribed its figures by hand.

The chart already carried strategy: Recreate, with a comment claiming it prevents exactly this. It does not, and it had never been tested: Recreate did what it promises and the archive was lost anyway. The comment is corrected rather than deleted, because a protection that was believed in is worth recording as one that was not — deleting it would leave the next reader free to reinvent the same belief.

What the fix guarantees. The collector now transcribes its own irreplaceable figures on the way out: on SIGTERM, after flushing its open window, the per-class high-water table goes to its own stderr — the one channel a terminating pod has that is not the volume it is about to release, and precisely the table a human copied by hand. soak.accessModes and soak.storageClassName are new and default to today’s behaviour, so an administrator with an RWX class can remove the handover entirely while nobody is required to have one.

Four alternatives are rejected in comments: RWX as the default (uninstallable on the clusters this kit is most useful on), a preStop hook (its output goes nowhere the kubelet keeps), writing the report to the volume (the thing that may be unreachable), and a ConfigMap or Event (a write verb held open for a fortnight). And the gap nobody had written down: hack/soak/ had no reset procedure at all — it was written for one campaign, and the improvisation it invites is undone within minutes by an autosync reconciler. It is documented now, in order, including which zeros a freshly started collector legitimately reports, so that nobody restarts it in a panic and loses the session.

What the reader should not conclude. The soak kit is not part of this suite and none of this is measured here. It matters to the page for one reason: the fortnight-long soak is one of M6’s two unmet exit criteria, and this lot is what makes a fortnight survivable. Its status is at the bottom of the page, unchanged in kind by anything the campaign found.

How the reuse was decided, and why the method matters more than the answer. The mover and sync digests are v0.6.5’s, unchanged. The intersection between go list -deps ./cmd/crystal-mover and every directory changed since v0.6.5 — commits and working tree — is empty. That is the whole argument, and it is an argument about a dependency graph rather than about a directory. 0.6.5 got this same judgement wrong in the other direction, and its report says so: git rev-list --count v0.6.2..HEAD -- cmd/crystal-mover returned 0, which was read as “the image is unchanged” while the binary linked api/v1alpha1, which had changed. A per-directory commit count says nothing about what a binary links. The conclusions differ between the two releases; the method that produced this one is the one that would have caught the other. The sync image carries the same binary, so the same dependency graph, and that one measurement covers both.

All three are multi-arch index digests, resolved with imagetools inspect, and all three were verified as the images actually running on the cluster before the run started.

The cluster. A freshly provisioned six-node RKE2 v1.35.7+rke2r1 — three masters, three workers — on Ubuntu 24.04.4 LTS, kernel 6.8.0-117-generic, with rook/ceph v1.19.0, Longhorn, local-path and real Hetzner Object Storage as the S3 backend. Five storage classes are present: ceph-block (the default), ceph-filesystem, longhorn, longhorn-static and local-path — the last of which is the class without snapshot support, and it is there deliberately, because “a volume nobody can snapshot is Skipped, not Failed” is a criterion that cannot be tested on a cluster where every driver works.

The suite delta

The same 93 checks as 0.6.5, and the one line of the suite that changed is the one that failed run 1

Measured, not assumed. Since v0.6.5, exactly one file under test/crucible/ changed — tests/m1_helpers_test.go, the wait bound described in the next section — and no check was added and none was removed. The suite is the same 93 checks 0.6.5 was accepted on, which the verdict’s own total independently confirms: a suite that had gained or lost a check could not report 93 of 93.

That is the whole delta, and it is worth stating for two reasons. First, it makes the non-regression claim legible: every one of these 93 checks had been passing before this release, so a green run is a comparison against a known result rather than a fresh set of assertions written after the fixes they bless. Second, it is the honest framing of what this release did not do. 0.6.5 added three checks and they found a defect on a whole plane of the product. 0.6.6 added none — and the gaps that would need new lanes, above all a hook chain driven on real storage, are named at the bottom of this page rather than closed.

How this campaign behaved

Two attempts, and run 1 was red on the measuring instrument rather than on the product

This section is a standing part of these reports and it is not decoration. A campaign that is re-run until it is green and then published as if it had been green the first time is the exact dishonesty this project keeps finding in its own artefacts and removing. 0.6.4 published a campaign that was killed mid-run with no verdict and said so. 0.6.5 published a red first attempt in which 21 of its 93 checks never ran, and that red attempt is where its most valuable finding came from. So: both attempts behind this verdict, and this one is published even though what it measures is the harness.

Attempt Result Coverage Wall clock
run 1 92 passed · 1 failed — the M1 helper m1WaitRepositoryInitialized, timed out 93 of 93 ran 3h10m55s
run 2 93 passed · 0 failed · 0 skipped — the verdict at the top of this page 93 of 93 ran 2h50m16s

What the single failure was, precisely. m1WaitRepositoryInitialized gave up at 300.001s waiting for a shared repository to report itself initialised. The repository had been initialised — in the same second the helper gave up — and the operator’s own measurement of the work was 462ms. So the two numbers to hold together are 300 seconds of waiting and 462 milliseconds of work: nothing was slow, and nothing was wrong with what the product did. The bound was a test-harness bound with no margin for a cold first pass on a freshly seeded cluster — the first repository initialisation of a campaign, behind image pulls and a cluster that has just been handed thirty-three namespaces of seed data. It was raised from 5 to 10 minutes, and that raise is the only change to test/crucible/ in this release.

Two things this must not be read as. Not a product defect: no phase was wrong, no data was at risk, and the operator’s own timing says the work took under half a second. And not harmless in principle either — a bound with no margin is a bound that will fire again, on somebody else’s slower cluster, and it will fire as a product failure on the face of it. That is the same shape as everything else on this page: an instrument reporting something other than what it is pointed at. A check that goes red without the product having done anything wrong costs exactly what a check that cannot go red at all costs — the reader’s ability to believe the next verdict.

Why it is on the page. Because the rule these reports follow is that a red attempt is published rather than quietly replaced, and the rule does not have an exception for the flattering case. This is the flattering case: the failure was in the suite, the product was fine, and the temptation is to file that as noise and print one number. 0.6.5’s red run found a real leak and was worth publishing on its own merits; this one is worth publishing because the rule does not depend on what the red run turns out to have found.

The whole suite follows, in the order and grouping the run reported it. Check names and durations are reproduced verbatim — including the ones that read 0s, which are separate verdicts on one measurement rather than checks that did nothing. Repository assertions still go through an independent restic oracle, a throwaway Job running the plain restic CLI, so a controller that both writes and reports the same wrong thing cannot make a check pass. Durations are not comparable between campaigns: several of these lanes wait out a real deadline, and one re-reads a repository whose size depends on everything that ran before it.

What this report does not say

Most of what this release changed is not driven by any lane here, and the release’s own subject is why that has to be written down

v0.6.6 is offered for testing in real conditions by early adopters, not for production. Everything below is still true after 93 green checks, and this page would be easy to read as claiming otherwise. A release whose subject is checks that cannot fail has no business publishing a verdict wider than its evidence:

  • Not one of these 93 checks was written to test anything this release fixed. The suite is 0.6.5’s, unchanged but for a wait bound in a helper. That is what makes the run a clean non-regression comparison, and it is also the reason every bullet below exists: a green gate composed entirely of older assertions can only tell you that the fixes broke nothing it already watched.
  • This campaign does not certify CI, which is where the release started. The 9-of-10 figures are read out of build history, and the three findings are verified by two gates going green on a cold runner. That is a different surface from this one. The lasting change — a purged analysis cache and a GOOS=linux pass — is a change to what a local gate can see, and nothing here measures it.
  • The two hook-chain fixes are covered by unit and envtest coverage only. The aborted quiesce that left applications frozen, and the Fail-policy post-hook that thawed the wrong pod, are both closed in this release — and no lane in this campaign drives a hook chain on real infrastructure. That gap was stated in 0.6.5’s report while the defects were open; it is still open now that they are fixed, which is the more uncomfortable half to write.
  • The errored-pass sweep is a static result. Two independent methods agreed on seven instances in three controllers and zero in ClusterErasure, but no lane makes the apiserver refuse a status write at a chosen pass. This campaign is evidence that reordering writes in four controllers broke no outcome the suite pins — not evidence that the class is now empty. The sweep covers five controllers; it does not claim to have covered every reconciler in the tree.
  • Neither dead protection is exercised here. No lane waits out an object lock for an hour, so the corrected recheck cadence and the transition-only ErasureBlocked Event are unmeasured on this page — the suite’s Immutable check returns in well under a second and asserts the phase, not the cadence. And the external-sync write had no live defect to begin with: its guarantee is structural, and a green run cannot show the absence of something that was never reachable.
  • The stuck-snapshot observation has nothing to observe on this cluster. Its cause was a CephFS csi-snapshotter feature-gate mismatch on somebody else’s cluster, and the campaign’s snapshotters work. The one-hour grace and the 2h ceiling that constrains it are argued and unit-tested, not timed here. Being deliberately an observation and not a verdict, it also cannot be caught failing by any phase assertion.
  • Three of this release’s subjects were found outside this suite — the fourth release running. CI’s build history, a production cluster that had never once backed up a CephFS volume, and a GitOps autosync that took the collector’s pod at the worst possible minute. Four releases in a row have been driven by findings this campaign could not reach, and saying so is cheaper than pretending the suite is the reason the product improves.
  • A green run is a sample, not a proof. Timing-dependent defects in this project have historically appeared roughly one run in three, which is why M4 was accepted on seven independent lanes rather than one. Read the verdict as one session on one cluster — and note that this release’s own two attempts differed by 20 minutes of wall clock on the same tree, which is the scale of variation a single 300-second bound had no margin for.
  • The fortnight-long soak has started and is not finished, and the pilot rollout has not started. Both are M6’s own exit criteria and both remain unmet. The soak is running on a real build cluster, on 0.6.5 — not on the release this page is about — for a 15-day window, which is the first time either criterion has moved from calendar work not yet begun to calendar work in progress. Nobody has finished the fortnight, and no result from it is on this page.
  • The PodSecurity review as a written document is still not written. The posture the operator’s namespace must carry is enforced by the chart and checked at startup; the review itself remains an outstanding obligation, as it was in the previous three reports.
