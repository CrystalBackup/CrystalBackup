Crystal Backup · Crucible acceptance

0.6.5 — One volume held the queue, and every night after it was skipped

The first 93-check run: 0.6.4’s suite had 90, and the three added here reproduce a real incident — one statically provisioned NFS volume, first in its namespace’s queue, that cost a live cluster thirty-one hours of backups. It also took two attempts. The first run of this same tree failed, and it failed badly: 62 passed, 7 failed, and 21 of 93 checks never ran because a single leaked VolumeSnapshotContent spent the suite’s four-hour budget sitting out deadlines. That leak was a real product defect. It is fixed, and the two checks that had timed out on it now pass in 50.9s and 15.8s.

The incident behind the release was quiet, which is the whole problem with it. A nightly ClusterBackupSchedule on a live cluster produced nothing for thirty-one hours. Nothing crashed. Nothing alerted above warning. The operator’s own dashboard read 0% backup success — which was true, and which nobody could act on because every number around it was either silent or wrong. The cause was one PersistentVolumeClaim, in one namespace, out of thirty-three: Bound, 200 GiB, a hand-made NFS PersistentVolume naming storageClassName: slow — a StorageClass that does not exist as an object. That is not a misconfiguration. For a static binding storageClassName is only a matching label between claim and volume, and Kubernetes never requires the class object to exist. The operator resolved that PVC’s snapshot capability through its StorageClass, got StorageClass "slow" not found, and returned an error — so Reconcile re-drove the same volume forever and the five volumes behind it in that namespace were never attempted at all. The run never went terminal, so concurrencyPolicy: Forbid skipped every following night.

Context, not measurement: that story comes from a user’s cluster and from the fix’s own unit and envtest coverage, not from this campaign. What this campaign contributes is three durations, on three checks that did not exist a week ago, and one of them is the number worth reading on this page: puts the neighbouring volumes' actual bytes in the repository, retrievable at 33.3s. Not attempted, not enumerated — read back out of the repository by an independent restic process while the broken volume sits first in the queue. On the live cluster that number did not exist for thirty-one hours.

What this report is not hiding

This was the second attempt. The first one failed, and 21 of 93 checks never ran

Run 1, on this same tree: coverage 69 of 93 checks (74% of the suite) — 62 passed · 7 failed · 3 skipped with a stated reason · 21 never reached, in a run that hit the harness’s four-hour ceiling exactly (4h0m0s). Its own verdict line said so in the first person: “This run did not finish the suite … the rest is unknown, not fine.”

Read the reasons column below rather than the count. Five of the seven sat out a full 600-second deadline and a sixth sat out 2700 — that is 95 minutes of a four-hour budget spent waiting on deadlines, which is why the seventh does not have a deadline of its own: it was killed by the suite clock while the budget was gone. The single cause was one leaked VolumeSnapshotContent from the namespace-plane lane, snapcontent-23f7c113. It was still there three hours later, so it was a permanent leak, not a slow one.

All five of the 600-second failures are the same object, and that is measured rather than inferred: every occurrence of the leaked content’s name — snapcontent-23f7c113 — in run 1’s log, attributed to its enclosing spec, lands in exactly five specs across four milestones. Four are residue checks doing precisely the job a leaked object exists to fail: M1’s leak-check, M5’s, and both of M6’s.

The fifth is the M3 DR bootstrap, and it is the one worth naming. It failed in an [AfterAll] — its own teardown’s residue check — and not on anything about disaster recovery. From the failure list alone it reads as a DR defect, and that is how it was first read and first reported, before anyone grepped the object’s name out of the log. It was never a DR failure. The only genuinely unattributable failure in run 1 was M4’s maintenance retry, the 2700-second one, and the M6 fidelity check never ran at all — the suite clock cut it. Both pass here, on the same tree.

The correction is worth more than the count. The obvious reading of a red run produced a wrong attribution that was published before it was checked, and only counting occurrences of one object’s name in the log settled it. A red run is not self-explaining: it invites exactly the kind of plausible story that a green run is usually accused of hiding.

Why this is on the page at all. A campaign that is re-run until it is green, and then published as if it had been green, is the exact dishonesty this project keeps finding in its own artifacts and removing. The previous release published a campaign that was killed mid-run and said so. This one published a red one. The leak was found by run 1 — the failure is where the value was.

What the red run found

Three code paths were blind to the same object, because a label was stamped with an empty value

Exposure objects are selected by (managed-by, cluster-backup, namespace). On the namespace plane there is no run — a Backup there is not a fan-out child — so the middle value was the empty string, and the same hole opened in three places at once:

  • exposureResidueRemains, the sweep’s own verification read — the thing that decides whether the “exposures cleaned” marker may be stamped. Its selector matched the wrong set, it answered no residue, and the sweep declared itself finished without having looked at the objects it exists to check. Its own comment already said never let an unreadable cluster read as a clean one; nobody had extended that to a selector that cannot match.
  • OrphanReaper.orphaned, the backstop, short-circuited on run == "" — one branch above the verdict this object needed.
  • reclaimOrphanOriginVSC, the crash-window reclaim written for exactly this situation, for the subtlest reason of the three: mergeLabels skips a write when the value already matches, and an empty desired value compares equal to a missing key. So created objects carried the empty label while the patched origin content — the cluster-scoped, expensive one — never carried the key at all.

The one component that read the cluster honestly was selfcheck, which selects on managed-by plus the PVC label and resolves no owner. The component that only observes was right; the three that act were wrong. The fix is structural rather than a wider selector: a new crystalbackup.io/backup label carrying the owning Backup’s name, stamped unconditionally on both planes, and no key is ever stamped with an empty value again — which removes the trap rather than the symptom. Pre-upgrade residue, which has neither label, is resolved by exclusion, because without that an upgrade would have converted already-leaked residue into permanently-leaked residue — including the object this campaign found.

What was under test

Three images, all three rebuilt, and a git count that proves less than it looks like

Reusing an image digest across releases is the kind of claim that has to be checked rather than assumed — a previous release contained an incident in which a silenced build step reused a three-day-old package and published an image byte-identical to its predecessor’s, exiting 0. So, plainly: all three images were rebuilt for this campaign and all three digests are new. A campaign has to test the artefacts the tag will publish, and carrying 0.6.4’s mover and sync digests forward would have validated artefacts v0.6.5 is never going to ship.

All three are multi-arch index digests, resolved with imagetools inspect, and all three were verified as the images actually deployed on the cluster before the run started — which is the half of the claim a digest alone does not make.

There is a true “unchanged” here, and it is narrower than an image. git rev-list --count v0.6.2..HEAD -- cmd/crystal-mover cmd/crystal-sync returns 0: not one commit has touched either directory across three releases, so the mover’s own code is the same. That count is the right evidence for that sentence and for no larger one. It does not license “the image is the same” — and reading it that way is this release’s own defect in miniature: a checked fact used to support a claim wider than itself, which is exactly what a StorageClass name was doing to a volume’s identity.

The images differ because the binary does not end at its own directory. crystal-mover links api/v1alpha1 and internal/apiconst, and both changed in 0.6.5 — firstAttemptAt, phaseEnteredAt, HookStatus.OnError and PVCSelector.Matches in the first, LabelBackup in the second. go list -deps ./cmd/crystal-mover was run before the build rather than appealed to afterwards, which is what turned “probably identical” into a decision to rebuild all three.

And then a measurement rather than an argument. The first build of this cycle produced mover digest sha256:87eb94f6…. That build was wrong for an unrelated reason — a package index that had been deleted made apko resolve restic from somewhere other than the local repository — and the corrected rebuild produced sha256:931c99ed…, the digest in the table above. Two different digests out of the same tree. Whatever else is true of this cycle, the mover image was not a fixed thing in it.

The third row is the one to keep. A check written to prove this release’s own fix is what found an unrelated, older, worse defect on a whole plane of the product — and it found it by failing. And the delta is the whole delta. Three new checks, in one lane, against one injected shape. The other 90 are the non-regression gate, unchanged in wording from 0.6.4’s campaign — which is what makes the five red specs in run 1 legible at all: they are checks that had been passing for releases, so a leak could not be mistaken for a check that had never worked.

Also

Three things worth recording about how this campaign behaved

None of the three is a product defect, and all three bear on how much the verdict at the top is worth.

the instrument

The red report refused to round itself up

Run 1 could have read 62 passed and been filed as nearly green. Instead its own headline was “FAIL — and this was a PARTIAL run”, with a per-milestone list of what never executed and a sentence saying the rest is unknown, not fine. That framing is what made a second attempt obviously necessary rather than optional.

product

The leak detector and the reaper disagreed, and the detector was right

The same binary shipped a reaper logging reaped 186 times for three objects it never deleted, and a leak detector correctly reporting eight residual objects, the oldest 31 hours old. A successful DELETE means accepted; with a finalizer, that and gone can be separated by forever. Only a confirmed absence may be called a reap now.

campaign 1 of 2

A four-hour ceiling is a measurement too

The suite stopping at exactly 4h0m0s is the harness doing its job: an unbounded run is how the product’s own thirty-one-hour stall stayed invisible. The ceiling converted one leaked object into a loud, dated, unmistakable red verdict instead of a campaign that ran all night.

What this report does not say

The guarantee is bounded by the shapes the suite injects, and three of them it does not

v0.6.5 is offered for testing in real conditions by early adopters, not for production. Everything below is still true after 93 green checks, and this page would be easy to read as claiming otherwise:

  • The release’s central guarantee is that no single volume can hold its namespace’s queue, and this suite proves it only for the shapes it injects — an unsnapshottable static volume, a missing snapshotter Secret, a snapshot nobody picks up, a mover pod that never starts. It does not inject a durably failing Expose, an unreadable source PVC, or a hooks-resolution failure. Those three are covered by envtest and by mutation testing against a stub, not by real storage.
  • Two hook-chain defects are covered nowhere at all — they are open. onError: Continue and the post-hook release path were both documented and both unhonoured; the fixes are in this release, and no lane in this campaign drives a hook chain on real infrastructure.
  • The defect this release fixes was found on a user’s cluster, not by this suite — for the third release running. A nightly schedule, a hand-made NFS volume, nothing exotic. Three releases in a row have been driven by findings this campaign could not reach; the countervailing fact is on this page, which is that run 1 found a defect nothing else could have.
  • The namespacesFailed trigger is not fully enumerated. A run reporting 32 failed namespaces where 29 Completed and 3 PartiallyFailed was reproduced from one path, and the same disagreement was afterwards seen on a fresh run whose children were stamped correctly. The counters are now derived from one classification with a total the controller checks, so the symptom cannot recur — but cataloguing every path into the collision branch is open in the backlog, and this campaign does not close it.
  • A green run is a sample, not a proof. Timing-dependent defects in this project have historically appeared roughly one run in three, which is why M4 was accepted on seven independent lanes rather than one. This release has exactly two campaigns behind it and one of them was red.
  • The two-week soak alongside an incumbent tool has not happened. Neither has the pilot rollout. Both are M6’s own exit criteria and both remain unmet. 0.6.2 built the instrument, 0.6.3 fixed a version-attribution defect in it, and 0.6.5 gave it a selfcheck that answers what will and will not be backed up. Nobody has run the fortnight.
  • The thirty-one hours are reconstructed, not replayed. No lane here runs a schedule for thirty-one hours, and none reproduces the Forbid chain that turned one stuck run into a month of skipped nights. What the new checks assert is the property that breaks the chain at its first link: the run goes terminal.

Run it on a cluster whose loss you can absorb, alongside — not instead of — whatever you back up with today. Before installing, run preflight.sh and then snapshot-probe.sh; preflight.sh’s new bound-volumes check is the one that would have named the volume in this story, and a PVC naming a class that does not exist is reported there as normal and nothing to correct, because it is. Then run selfcheck --format text, which now reports the PVCs selected by no schedule and the PVCs selected only by a schedule that cannot fire — covered on paper, unprotected in fact.
