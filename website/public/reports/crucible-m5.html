This is the M5 acceptance gate — the fourteen new criteria run under the m5 label against a live cluster, with an independent restic oracle (a throwaway Job running the plain restic CLI against the same repositories) so a controller that both writes and reports the same wrong thing cannot make a check pass. The 47 skipped lines are the platform / M0–M4 checks that belong to other labels; they ran green in the same session’s full-suite non-regression pass (60 passed, 0 failed, 1h23m).

Writing and running this suite found six defects, and three of them left an advertised M5 feature completely inert: a namespace-plane external sync could never reach Completed, mode: Mirror never pruned anything, and the right to erasure never removed a snapshot. None was reachable without a real repository — in every case the visible step succeeded and the step after it failed, which is exactly why unit tests and a green CI had not noticed. The other three: a location alias slipped past the self-copy guard, rclone probed and would have created the destination bucket (fatal with the bucket-scoped credentials a least-privilege secondary should have), and a ClusterErasure panicked the reconciler on any location without a maintenance block — which is the default. All six are fixed, each with the regression test that would have caught it; the results below are the run after.

M5 · External sync — the second copy, under a second key

6 / 6

External sync’s claim is not that the bytes arrived. It is that the second copy is re-encrypted: restic copy decrypts from the source and re-encrypts to the destination’s own key, which is why the feature was chosen over server-side object replication that would have carried the source key into the secondary. A claim about keys can only be tested by trying the wrong one.

  • A narrowed sync copies only the selected namespace, and the copies are re-encrypted to the destination's own key 2m35.9s

    The copy runs through two independently-credentialed rclone remotes and lands only the selected namespace’s snapshots. Every copy records the source snapshot it came from (restic’s original) and carries a different ID — a content-addressed re-encryption under the destination key, never a byte clone.

  • The destination does NOT open with the source's key, nor the source with the destination's 20.7s

    Case 18’s core. The oracle opens each repository with the other repository’s DEK and restic refuses both times — then opens each with its own and succeeds, so the refusals are about the KEYS and not about two unreachable buckets. Client siloing holds: a secondary is opaque to the primary’s key.

  • Mirror propagates a source forget to the destination, and removes nothing else 1m10.8s

    A snapshot is forgotten at the source by explicit ID; the next Mirror run removes exactly its copy at the destination and leaves the surviving one — matched by original, not by tag or timestamp, which two runs of one schedule would not distinguish. restic check passes afterwards.

  • A sync onto its own location is refused at admission (rule 9) 0s

    A static ValidatingAdmissionPolicy rather than a controller check, so the guard holds even while the operator is down.

  • A sync between two DIFFERENTLY-NAMED locations that address one repository is refused by the controller 22.6s

    The case admission cannot see: an alias — a second location on the same bucket, prefix and cluster ID — passes a name comparison and is one repository. Writing this spec is what found that the controller’s own backstop compared repository names, which derive from location names and so only reproduced rule 9. It now compares the resolved repository URL.

  • The operator was deployed with a real sync image, not the chart's placeholder digest 0s

    A deployment check that fails fast. A sync image is pulled by nothing until an ExternalSync exists, so a forgotten digest is silent right up to an ImagePullBackOff inside a Job nobody is watching.

M5 · Namespace plane — the user’s repository, the user’s key

4 / 4

The milestone’s headline guarantee is negative: platform access ends when the user’s key does. platformAccess was specified, never implemented, and dropped — so the guarantee is bought by the mechanism not existing. That cannot be verified by reading the operator’s code; it is verified by asking the repository how many keys it holds.

  • Backs a tenant volume up to the tenant's own repository, readable with the tenant's own password 1m18.1s

    A real Ceph PVC reaches the user’s own prefix through the same execution path as cluster DR, with the S3 credentials read from their namespace. The oracle opens the repository with the password the test holds and finds the snapshot the Backup reported, tagged with this namespace and no other.

  • Holds exactly one key slot, and the platform holds no wrapped key for it (adr/0004 amendment) 3.7s

    restic key list reports one slot. A second would be a password living in crystal-backup-system that survives the user rotating their key — and because removing a restic key slot does not rotate the master key, one they could never take back. The operator namespace also holds no wrapped DEK for the location.

  • Loses platform access the moment the user deletes their password Secret — while the data stays readable to them 20.4s

    Deleting the Secret takes the platform’s access away, generates no replacement password (a dangling reference must be an error, never a new key), and leaves the backups intact and still openable with the key the user kept. Without that last half, “the platform lost access” would be indistinguishable from having destroyed the repository.

  • Left no residual snapshot objects behind 50.9s

    The namespace plane runs the same exposure machinery as cluster DR — a tenant VolumeSnapshot, a static VS/VSC pair and a clone PVC in the operator namespace — so it inherits the same leak surface and gets the same check. The tenant namespace is then torn down through the strict helper that fails if it never disappears.

M5 · Right to erasure — physical, verified by re-scanning

4 / 4

“The deletion happened” is the only thing a GDPR request asks, and a controller reporting Completed only says it ran the commands. So the suite erases for real and re-scans the repository with upstream restic — the evidence a data-protection officer would want.

  • Parks an unconfirmed erasure and names what it would remove (R23) 1m41.9s

    An absent confirmation parks the object rather than rejecting it, so the destructive act is deliberately two steps: create the intent, read what it says it will remove, then type the identity back. Nothing is erased while it waits.

  • Refuses a confirmation that does not name the target, at admission 0s

    A wrong confirmation is denied by the API server, so the guard holds with the operator down.

  • Physically removes exactly the confirmed namespace, leaving its neighbour and the repository sound 38.8s

    The count written before the forget matches what goes; a re-scan finds none of the erased namespace’s snapshots and all of its neighbour’s — tag scoping is the only thing standing between one tenant’s erasure request and another tenant’s backups. restic check passes after the prune repacked the repository.

  • Is Blocked, not Completed, on an Immutable location 400ms

    Object Lock forbids the deletion, and reporting success while the objects are still there is the worst possible answer to an erasure request. The erasure parks in Blocked with a zero count.
