This release was validated differently, because M4’s hardest bug demanded it. A three-lane fanout kept reproducing (~1 run in 3) a leaked VolumeSnapshotContent — deletionPolicy: Retain, no owner, invisible to every GC — and the audit that followed proved the teardown was structurally one-shot: the reconcile pass that persisted a Backup’s terminal status was the only pass that ever deleted its snapshot pair, and nothing, orphan reaper included, ever retried. The fix is crash-only re-entry (a terminal Backup is re-swept until nothing remains, then stamped exposures-cleaned), and the acceptance for it is statistical: seven independent full-suite lanes, seven times zero residual snapshot objects, including a new spec that SIGKILLs the operator at the exact terminal-transition instant the leak lived in. The verdict above is the final lane, run on the released image. As always, every repository check goes through an independent restic oracle, so a controller that both writes and reports the same wrong thing cannot make a check pass.

M4 · Repository maintenance & verification (R17)

3 / 3

Scheduled prune and check on the per-repository exclusive queue — reclaiming what retention freed, and verifying that what the repository holds is still readable, without ever racing the backup plane.

  • Holds the prune until the backup's movers have drained, then runs it exclusively 7m4.3s

    A prune due while a backup is running never starts alongside a live data mover: admission holds new movers back, the drain waits the in-flight ones out on its own short deadline, then the prune runs alone and succeeds — and restic check is happy afterwards (adr/0015).

  • A killed prune is absorbed by the Job retry: a terminal outcome is recorded and the repository is not wedged 8m8s

    SIGKILLing the prune mid-flight orphans restic’s exclusive lock; the maintenance Job’s pod-level retry absorbs the kill, a terminal outcome lands in status.recentMaintenance (so the cron baseline advances), and concurrent --no-lock reads never block.

  • Tampering is caught by check --read-data-subset and surfaced on the repository 3m0s

    Bytes flipped inside a pack object in S3 are found by the scheduled check --read-data-subset — silent bit-rot a structural check cannot see — and surfaced as lastCheckResult: Failed plus the RepositoryCheckFailed condition and alert metric.

M4 · Crash-only teardown — the leak audit’s gate

3 / 3

The teardown that used to get exactly one chance now converges by re-entry, whatever instant the process dies. These three ran green in every sampled lane.

  • The operator SIGKILLed at the terminal transition still converges to zero residual snapshot objects 58.3s

    The new aimed spec: watch a child Backup at 200ms and grace-0 kill the operator the instant the terminal phase appears — inside the exact [status write → teardown] window the leak lived in. The fresh operator’s re-entry sweep finishes the teardown, stamps exposures-cleaned, and the leak-check finds nothing.

  • Leak-check — a run leaves zero residual snapshot objects 5m22.9s

    After a full multi-namespace run: zero CrystalBackup-labelled VolumeSnapshots, zero attributable VolumeSnapshotContents (cluster-scoped included), zero temp clone PVCs — measured independently of the operator’s own accounting, in all seven lanes.

  • The operator killed mid-run converges via Job re-adoption 5m30.6s

    The historical restart criterion: killed mid-run, the fresh operator re-adopts the in-flight mover Jobs (same UID — never duplicated), drives the run terminal, and the leak invariant still holds afterwards.

What the campaign surfaced

Four findings only repetition on real infrastructure could produce

Running the same suite seven times on seven clusters is what turned three distinct one-in-N defects from anecdotes into fixes — each round of the campaign caught a different one, none of which a single green run would have shown.

product

The teardown leak itself

One-shot teardown + a terminal short-circuit + a cluster-scoped Retain content no GC can reach = a permanent leak from a single ill-timed process death (or a status write that commits server-side while erroring client-side). Fixed by re-entry: sweep until nothing remains, then stamp; the orphan reaper now really does sweep VS/VSC as the slow backstop.

product

“Deletes issued” is not “nothing remains”

A validation lane caught the sweep stamping its marker while the external snapshot-controller was still draining a content (~10 minutes under load). The marker now requires a verified-empty read — and each re-verify pass actively accelerates the drain by reclaiming directly.

product

Back-to-back maintenance ops raced a grave

Op B, queued behind op A under the same deterministic Job name, could adopt A’s foreground-deleting Job — which vanished mid-poll (a spurious Failed record) or could even hand B a success it never earned. A terminating grave is now waited out; only a live leftover is adopted.

test harness · ops

The harness had to earn seven clean measurements

Ginkgo enforces its own suite timeout (a lane announcing 120m was silently cut at Ginkgo’s 1h default — a truncated run reports specs failed that were merely cut off); transient Ceph HEALTH_WARNs on ephemeral VMs get a bounded window to clear; a residual measurement that cannot read the cluster records ?, never 0; and a Hetzner-side volume lock taught the fanout to sidestep poisoned lane names.
