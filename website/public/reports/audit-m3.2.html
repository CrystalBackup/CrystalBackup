M3.2 Restore Safety

The M3.1 audit closed one open item with a reproduction plan instead of a patch, because two explanations called for opposite fixes. Reproducing it took five minutes — and turned up three bugs on the restore path, the worst of which deleted the volume it was restoring.

Method one crucible label (m2) alone, on a fresh RKE2 / Ceph cluster Instrument the API server’s own managedFields, snapshot-controller logs, rbd ls Date 2026-07-25 Outcome 0.3.2
The RBD image did not vanish. We deleted it.

M3.1 left this open with two candidate explanations: a Ceph-side loss, or a teardown releasing a PersistentVolume under a Delete policy — which would be a data-destruction bug, not a flake. It was the second one, and the mechanism was not teardown at all. A Restore in Recreate mode deletes every selected resource before recreating it from the backup, including the PersistentVolumeClaim. Deleting a PVC releases its PersistentVolume; a dynamically-provisioned volume’s reclaim policy is Delete; the CSI driver therefore destroyed the user’s RBD image as a side effect of restoring a manifest. The data half of the same restore was already mounting a twin PV built from that volume’s handle, so it hung forever on internal RBD image not found — restoring a volume that had been deleted underneath it.

Three bugs, one reproduction

FindingEvidenceFix
Recreate destroys the volume
data loss		 The twin PV named csi-vol-1ba1bab4…; that image was absent from rbd ls blockpool, and PVC data had rebound to a brand-new empty volume. The restore sat 20 minutes in ContainerCreating. PVCs and PVs are reconciled in place even in Recreate mode. Nothing is lost: the mode’s promise for the contents is delivered by restic restore --delete on the data path, and the manifest half’s job for a PVC is to create the claim when it is absent, never to replace a live one.
A restored finalizer makes a namespace immortal Namespace m2-restore stuck in Terminating on a PVC carrying pvc-as-source-protection with zero VolumeSnapshots in the cluster. The snapshot-controller’s log showed it adding that finalizer at 10:35:44 and removing it at 10:35:46; the PVC’s managedFields then named the culprit — manager: crystalbackup-restore, operation: Apply, at 10:36:38, owning f:metadata:f:finalizers. Sanitization rule S8 strips every finalizer at capture, and the applier strips them again on the way in so snapshots taken before 0.3.2 are safe too. Enumerating them by name is a losing game — every CSI driver and operator adds its own.
Recreate could never finish cleanly serviceaccounts "default" already exists → one resource Failed → the whole restore PartiallyFailed. The crucible’s m2 Recreate spec had never once passed. The control plane recreates a namespace’s default ServiceAccount the instant it disappears. An AlreadyExists on the recreate now falls back to the in-place apply, which converges on exactly what Recreate asked for.

Why the capture caught a finalizer at all

10:35:44 — snapshot-controller adds it
▲ 2-second window opens — a VolumeSnapshot names the PVC as source
between the two — the manifest dump runs
▲ Photographed — the finalizer is captured as if it were part of the object
10:35:46 — snapshot-controller removes it
✓ Window closes — the live cluster is fine
10:36:38 — the restore re-applies it
▲ One-way door — no VolumeSnapshot exists now, so nothing will ever remove it

A finalizer is not a property of an object, it is one controller’s claim on one live instance. The controller that would release it never saw the restored copy. It is rule S5’s failure mode with the sign flipped: a dangling ownerReference deletes what was just restored, a dangling finalizer makes it immortal — and takes its whole namespace with it.

Discovery keeps its inventoryA per-group projection failure aborted the pass before recording what it had just listed, so lastDiscoveryTime froze and every retry paid for a full re-listing from S3. Least privilege on maintenance moversThe capability set follows what a Job can touch, not what it is called. DAC_OVERRIDE exists so a data mover can walk a tenant’s files; a Job with no PVC mounted — init, forget, prune, check, snapshots, unlock and the manifest shapes — now adds nothing on top of drop: ALL.
A test that was not testing what it claimedThe OOM spec SIGKILLed whichever labelled mover pod happened to be Running — another run’s, or the same run’s manifest mover — after which the data volume completed normally and the spec failed on its own assertion. It is now scoped to its own run’s data movers. The operator’s crash handling was correct all along.
The next leak fails its own runSpecs that restore into a namespace tear it down with deleteNamespaceAndWaitGone, which surfaces the namespace’s own “finalizers remaining” message — instead of leaving the wedge for a later run to trip over.
