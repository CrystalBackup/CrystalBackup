Every previous edition of this page led with the same sentence: the suite passed. It is true again — 90 of 90, no label filter, 2h43m24s — and it is the least interesting thing on the page. Eighty-two checks passed three campaigns in a row, and for two of the four defects a user hit in their first hour, those checks were proving that a chart nobody installs works. test/crucible/deploy/deploy.sh set namespace.create=false and networkPolicy.apiServerPort=6443 before the first crucible run ever happened, the second with a comment quoting the operator’s startup failure verbatim. The workaround had been understood, written down and shipped in this repository for longer than the bug had been visible to anyone outside it.

So the number that matters in this run is not 90. It is eight: the checks the suite did not have before, in four new lanes. One of those lanes, m6/stall, was wrong in three different ways before it was right, and the operator was correct every time it said otherwise. It was loud about it, which is the only reason this paragraph exists: a lane that quietly verifies nothing is indistinguishable from a lane that verifies everything, for exactly as long as nobody looks.

What this run caught

The m6/stall lane shipped red, and needed three runs to become evidence

This lane exists because of the field report: six mover pods sat in ContainerCreating for thirty-six hours, the kubelet published the cause 1069 times, nothing read it, and nothing ever gave up. The lane injects the shape of that failure by parking the RBD node plugin DaemonSet, then asserts the volume fails on its own at the 30-minute mover-start deadline and that the operator’s status.volumes[].reason carries the cluster’s own words. It was wrong three times before it was right, and the operator was correct on all three occasions.

One: it reverted its own fault injection. The spec parked the DaemonSet and timed out after 300s waiting for the pods to go away. That reads as a slow cluster and invites a bigger timeout. It was not slow: rook ≥ 1.17 hands the CSI driver plane to a ceph-csi-operator that owns that DaemonSet through a csi.ceph.io/v1 Driver CR and reconciles it on an Owns() watch. The campaign recorded six SuccessfulDelete and six SuccessfulCreate events carrying the same timestamp, with “node plugin daemonset updated successfully” in the reconciler’s log between them. The park did take. It lasted a fraction of a second. No timeout would ever have worked, because a reconciler is not a race you can wait out. The fix is to stop the reconciler before touching the object — the pattern m6_precheck_test.go already used on rook-ceph-operator — and to restore it after the unpark, in that order. Setting the Driver CR’s own nodePlugin affinity instead was rejected: rook rewrites that CR on every CephCluster reconcile, so a reconcile inside the spec’s 45-minute window would have un-injected the fault silently and made the lane flaky rather than red.

Two: it asserted a word nobody emits here. With the fault finally holding, the spec required the reason to contain FailedMount — the word from the field report. But this injection produces a different stage of the same failure. Parking the node plugin also removes the driver-registrar, so the driver leaves the CSINode object and the attach-detach controller refuses before the kubelet ever reaches MountDevice:

FailedAttachVolume — AttachVolume.Attach failed for volume "pvc-…" : CSINode <node> does not contain driver rook-ceph.rbd.csi.ceph.com

Both messages are the cluster saying why; only the stage differs. Written the other way, the spec asserted how its own fault injection happens to fail, and it cost a campaign to say so.

Three: it paraphrased the product. The next draft required the Backup’s Warning Event to say “never reached Running”. The operator says “no pod of it ever reached Running”. A one-word difference between what an author remembered writing and what the code emits, and a red lane against a correct product.

What the assertions do now. They read the Warning Events the cluster actually recorded on the mover pod, and require the operator’s reason to quote one of them — whatever this cluster’s failure stage turns out to be — rather than comparing against a string chosen in advance. An explicit guard fails the check when that Event set comes back empty, so a run in which the cluster recorded nothing cannot pass vacuously by finding no contradiction. A spec written against an imagined message tests its author’s imagination, which is the same family of defect as a campaign run against a chart nobody installs. Both were found in this cycle, in different parts of the repository, days apart.

What the campaign installs now

Every --set is documented, or it is a bug in the defaults

The two overrides are removed, and the rule that replaces them is written into deploy.sh itself: every --set in the crucible’s install is either something the documentation tells a user to set, or it is a bug in the defaults. The defaults changed to meet that rule rather than the install being adjusted to tolerate them.

namespace.create now defaults to false. The documentation provisions the cluster KEK Secret into crystal-backup-system before helm install runs, and it has to — the KEK is escrowed out of band and this chart never creates a Secret. So the namespace already exists, and a chart rendering a Namespace object asks Helm to adopt it, which it refuses with an ownership-metadata error on the very first command. Two of the three install pages already told the reader to turn the default off. When the documentation for most install paths tells you to disable a default, the default is wrong.

networkPolicy.apiServerPort is now apiServerPorts, a list, defaulting to [443, 6443]. On k3s, RKE2 and kubeadm the kubernetes Service listens on 443 and kube-proxy DNATs to the API server’s Endpoints on 6443 before the CNI evaluates egress, so a rule naming only 443 never matches the packet that leaves the pod and the operator never starts. The superset is deliberate: the chart cannot know which port a cluster uses, and one extra outbound TCP port to a destination that is already the API server does not compare with an operator that never comes up.

Three --sets remain in this campaign’s install, and all three are now on every install page: metrics.serviceMonitor.enabled, metrics.rules.enabled and networkPolicy.monitoringNamespace. Observability is opt-in, and off means no alerts — which is load-bearing for this suite, because the M6 alert checks below are only legitimate if a reader can reach the same configuration by following the documentation.

What was under test

Three images, and why two of them are the same as last time

Reusing an image digest across releases is exactly the kind of claim that has to be justified rather than assumed — this release also contains an incident in which a silenced build step reused a three-day-old package and published an image byte-identical to the previous release’s, exiting 0. So: the operator image is new and is the one v0.6.3 ships. The mover and sync images are unchanged since v0.6.2, and that is correct rather than convenient.

The reason the mover image did not need rebuilding. cmd/crystal-mover has not been touched since the v0.6.2 tag. What changed is what the operator asks for; what executes the ask is the same binary. The same holds for sync.

Also

One lane that passed first time, and two things found off the cluster

Not everything new in this campaign needed three attempts. The other two items are not product defects and neither could corrupt a backup, but both are the same shape as the release itself: a step that declines to do the work and reports success.

ci

The gate exists, works and self-tests — it just ran only in CI, never in the local gates, so four days of local runs said nothing. It is now in the delivery runbook’s first-stage checks.

What this report does not say

M6’s two exit criteria are still unmet, and 90 green checks do not touch either

v0.6.3 is offered for testing in real conditions by early adopters, not for production. Everything below is still true after 90 green checks, and this page would be easy to read as claiming otherwise:

  • The two-week soak alongside an incumbent tool has not happened. Neither has the pilot rollout. Both are M6’s own exit criteria and both remain unmet. 0.6.2 built the instrument that would watch a soak; 0.6.3 fixed a version-attribution defect in it. Nobody has run the fortnight.
  • Four of this release’s five findings came from one user’s cluster, not from this suite. That is the whole point of the edition and it should not be softened by the verdict at the top. The suite has been extended so that two of the four are now reachable here, but the extension was written after being told what to look for.
  • A green run is a sample, not a proof. Timing-dependent defects in this project have historically appeared roughly one run in three, which is why M4 was accepted on seven independent lanes rather than one. This is a single session.
  • The stall lane tests the shape of the field failure, not the failure. The user’s krbd mapping error is not reproducible on demand, so the lane parks the RBD node plugin instead. That reaches the same operator guard by a different stage of the same fault — which is precisely the distinction that made the first two drafts of it red.
  • Two deadlines now exist where there were none, and neither covers a mover Job that has vanished. Every deadline here is measured against a durable clock belonging to the object being waited on; when the Job is absent there is no such clock, and the reconcile requeues forever. The new CrystalbackupBackupStalled rule is what covers that, and an alert is not a controller.
  • The PodSecurity review is partly executed, not done. The posture crystal-backup-system must carry is now enforced by the chart in three places and checked by the operator at startup, but the review as a document is still unwritten.

Run it on a cluster whose loss you can absorb, alongside — not instead of — whatever you back up with today. Before installing, run preflight.sh and then snapshot-probe.sh: the first reports every resolvable storage class as USABILITY NOT ASSESSED, which is the honest answer, and the second is what actually answers it by snapshotting, restoring and mounting on your nodes.
